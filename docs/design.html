The screens

Drawn at the real 320x240, with the proposed type scale and the Nightwatch palette. Amber is the radio, cyan is the broadcast, grey blue is every label.

Type scale

The current menu is a 16px bitmap font in 20px rows. That is the complaint, and it is the thing this scale exists to fix.

Why this face

  • Condensed
    A 320px wide screen has to hold six digits of frequency at 62px. A condensed face fits them without shrinking them. Roboto Condensed is Apache 2.0, converts cleanly with the LVGL font tool, and is a variable font, so any weight can be picked at conversion time instead of being limited to the weights the family ships.
  • Stroke weight
    Measured on the real font file, Roboto Condensed puts a 1.17px stem on the screen at the 13px label size, against 0.93px for Barlow Condensed. A stem under one pixel is carried entirely by anti-aliasing, which is what makes small labels look washed out on a dim TFT. 26 percent more ink where the text is smallest is the reason this face was picked.
  • Tabular figures
    Not optional. With proportional digits the frequency jitters sideways every time a digit changes, and on a tuning display that is the one thing you cannot have.
  • Weight, not size
    Labels and values are separated by weight and colour, not by making labels smaller. Today both are 14px in the same colour, which is why the screen reads flat.
  • Subset it
    The 62px frequency font needs eleven glyphs: ten digits and a point. Subsetting takes it from about 180KB to under 20KB. The whole scale lands around 100KB, against 8MB of flash.

The menu trade, stated plainly. Going from 20px rows to 36px rows means five rows on screen instead of ten. That is a real loss and it is deliberate. LVGL scrolls, so nothing becomes unreachable, and a row you can read at arm's length beats two you have to squint at.

How it is built

Five layers, one rule: the core must not know a screen exists.

board/     One header per board. Pin map, feature flags.
           board_ats125.h, and the next radio is another header.

drivers/   tef668x, display, touch, encoder, keypad, rtc, battery.
           Each behind an interface. No globals.

core/      Tuner state machine, RDS decoder, band plan, memory
           channels, settings, volume AGC.
           No hardware. No UI. Builds and runs on a laptop.

ui/        LVGL screens, menus, panels. Talks to core through an
           API. Never touches a driver.

net/       Wi-Fi, web server, OTA, NTP, telemetry.

Two FreeRTOS tasks. The radio owns core 0 and the 43 ms RDS cadence. UI and network own core 1. They pass a state snapshot and a command queue, never a shared variable. That is why a slow web request cannot drop RDS groups, which in the current firmware it can.

Build order

Audio early, polish late. No phase starts before the one before it is green in CI.

  1. Phase 0
    Escape the cable
    Partition table, Wi-Fi with access point fallback, over the air update, rollback armed. Flashed once over USB. The last time the boot button is ever needed.
  2. Phase 1
    Foundations
    Layer skeleton, board header, one environment per board plus native, and CI with a coverage gate. One passing test before anything depends on the test path.
  3. Phase 2
    It is a radio
    Tuner driver, patch load, capability detection, band plan, encoder and keypad. Plain text on screen. Done when it tunes a station and plays audio.
  4. Phase 3
    Core logic, tested on a PC
    RDS decoder, settings, memory channels, volume AGC. All of it under test with no hardware attached. This is the phase that justifies the architecture.
  5. Phase 4
    The interface
    LVGL, fonts, the panel set, per band layouts, menu, boot screen, recovery screen. The largest phase.
  6. Phase 5
    Web and telemetry
    Web server, access PIN, settings pages, memory editor, telemetry over UDP and websocket, diagnostics, backup and restore.
  7. Phase 6
    The rest
    Spectrum view, sleep timer, alarm, power management, and over the air updates straight from a GitHub release.

The decisions that matter most

  • LVGL
    Today every menu row is written twice, once for the encoder and once for touch. LVGL treats them as two input devices on one UI, so touch becomes a setting rather than a second codebase.
  • Settings struct
    One versioned struct in NVS, not hand written byte offsets. Adding a setting is adding a field. The web UI then comes almost free, because the struct serialises straight to JSON.
  • Named strings
    UI code says STR_VOLUME_AGC, never an index. Inserting a string can never shift another one. English ships, the mechanism for more stays.
  • Telemetry
    The radio broadcasts its live state as JSON. No debug builds, no cable. Captures become test fixtures, which is how the RDS decoder gets tested against real broadcasts rather than invented data.
  • Measured
    No threshold is guessed and no power saving is claimed until it has been measured. A guessed signal threshold made the volume AGC do nothing for a week, and it failed silently.
  • Recovery
    One screen reached by holding the rotary button, rendered with safe display settings so it works when the broken setting is the display. Not seven button combinations nobody remembers.

Other layouts

The FM and AM screens above stay as they are and remain the default. These are five other ways to arrange the same information on the same 320x240 screen, drawn with the same palette and type scale. Six layouts ship in total counting the default, and the user picks one in the menu or in the web interface. A layout is a table of panel placements held as one byte in the settings struct, the same way a theme is.

AM and SW follow whichever of these is picked. The RDS block has no job there, so the space it uses on FM goes to bandwidth, co-channel and tuning offset, as in the current AM design.

The band spectrum layout depends on a build flag. It needs FEATURE_SPECTRUM. On a board that has that flag at 0 the layout is not compiled and does not appear in the menu.

The cost of shipping four is testing, not flash. Six layouts across two band groups, with touch off and again with touch on, is twenty four manual checks per release instead of four.

Themes

Ten themes ship in the firmware. A theme is a named set of ten colour roles, held in the settings struct as one byte, so switching one repaints the screen and changes nothing else. Every screen, panel and menu draws from the roles, never from a hard coded colour, which is what makes a theme a setting rather than a build.

RoleUsed for
bgScreen background
barStatus bar and bottom strip background
primaryFrequency, panel values, the tuned thing
secondaryStation name, radio text, anything the broadcast sends
mutedLabels, units, scale numbers
textNeutral text such as the clock
okGood state: stereo lock, battery healthy, self test passed, low end of a meter
warnBad state: overload, low battery, a failed self test, high end of a meter
ruleDividers and panel edges
trackThe unfilled part of a meter

The same FM screen in all ten. Nothing moves between them, only the ten roles change.

Every theme carries rank. A theme where the frequency, the station name and the labels all sit at the same brightness reads flat, so a single hue at one weight is not shipped. Nightvision is the one exception, and it earns it: dim green with no white and no blue is what keeps night adaptation, and it still separates its four levels by brightness.

Grayscale carries rank by brightness alone, so it still reads on a panel with a bad colour cast, and it is what the recovery screen uses.

A theme is data, not code. Adding an eleventh is adding a row to the theme table. A custom theme set from the web interface is the same thing with the ten values coming out of settings instead of the table.

Which font

Three condensed faces, all open licensed and all convertible with the LVGL font tool. The same FM screen in each, everything identical except the family and the frequency size. The numbers below were measured with the real font files, not estimated.

x-height does not separate them. The x-height to cap height ratios are within two percent of each other, and all three land on the same 7px x-height at the 13px label size. The first version of this page argued from x-height and was wrong.

Stroke weight does. At the 13px label size Roboto Condensed puts 1.17px of stem on the screen, IBM Plex 1.05px, Barlow 0.93px. Below one pixel the stroke is carried entirely by anti-aliasing, and that is what makes small labels wash out on a dim TFT.

Width is the price. Roboto is 24 percent wider than Barlow, which costs 8 characters of radio text on a 300px line. It does not cost any frequency height: the row is wide enough that all three fit a 62px frequency. Roboto Condensed ships.

Where these mockups are not the truth

The dimensions are real, the palette is real, and the type scale is the one being proposed. But this is SVG in a browser rendering Roboto Condensed as a web font. On the radio it will be the same family converted to LVGL bitmaps at each fixed size, so hinting and spacing will differ slightly.

The meter bars are drawn here as smooth gradients. On the panel they are discrete two pixel segments with the ramp computed in HSV, so the real thing steps rather than glides.

Everything on these screens is example data. The station, the frequencies and the readings are plausible values, not a capture from the radio.
