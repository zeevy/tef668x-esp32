# Security audit report, 2026-09-12

**Overall status:** YELLOW
**Scope:** phase 0, `src/` and `platformio.ini` and `partitions.csv`. Phase 1 adds the build and CI surface, covered in its own section below.
**Standards:** OWASP Top 10 2021, OWASP ASVS L1 and L2, CWE, CVSS v3.1
**Threat model:** the attacker is on the same LAN as the radio, or within Wi-Fi range of it. There is no internet exposure. The radio serves plain HTTP on port 80 and accepts firmware uploads.

The OWASP checklists are written against web applications. This is ESP32 firmware in C and C++, so each category was translated rather than dropped. Where a control has no meaning here, that is said rather than left blank.

---

## Executive summary

| Severity | Count |
|---|---|
| Critical | 0 |
| High | 1 (1 resolved) |
| Medium | 3 |
| Low | 4 |
| Info | 3 |

**The three to fix first**

1. ~~**SEC-01.** The default access PIN is computed from the MAC address.~~ **Resolved.** The default is now 000000 with a warning on boot and on the page.
2. **SEC-02.** Firmware images are not authenticated. `Update` checks the ESP32 image magic and a checksum, which is integrity against corruption, not proof of origin. Anyone past the PIN can run any code they like on the radio, permanently.
3. **SEC-03.** Everything, including the PIN and the session cookie, travels in clear over HTTP. On the setup access point, which is open, every frame is readable by anyone in range.

**What is already right**

- No third party libraries at all. The only dependency is the Arduino ESP32 core, pinned to an exact version.
- Session tokens come from `esp_random`, which is the hardware RNG, and are compared in constant time.
- The session cookie is `HttpOnly` and `SameSite=Strict`.
- Network names are HTML escaped before being put in the page, so a hostile SSID cannot inject markup.
- The PIN attempt gate and its lockout are wrap safe across the 49 day millisecond rollover, and that is covered by a test.
- Every buffer write uses `snprintf` or a bounds checked copy. No `strcpy`, `sprintf` or `strcat` anywhere.
- The PIN is never sent to the browser.

## Findings

### SEC-01 RESOLVED, was HIGH, A07 Identification and Authentication Failures, CWE-340

**Resolved on 12 September 2026.** The MAC derivation was dropped. The default
PIN is now 000000, and a radio still on it warns on every boot and shows a red
banner on its own web page. The default is still not a secret, but it no longer
pretends to be one, and the user is told plainly to change it. Decision 14 in
`DECISIONS.md` was rewritten to match.

The original finding follows, for the record.

**The default access PIN is computable by anyone who can see the radio.**

**File:** `src/core/access_pin.c:12`, used from `src/main.cpp:88` and `src/net/web_update.cpp`

**Description.** `accessPinFromMac()` is FNV-1a over the six MAC bytes, modulo one million. The algorithm is eight lines of GPL source in a public repository. The MAC is not a secret: it is in the header of every 802.11 frame the radio sends, in clear, even on a WPA2 network, and `arp -a` returns it to anything on the LAN. `board_ats125.h:19` also puts the last two MAC bytes into the setup access point SSID.

**Attacker action.**
1. Sit within radio range, or on the same LAN.
2. Read the MAC. From the LAN, `arp -a` after one ping. From the air, any captured frame header, or the AP SSID plus the Espressif OUI leaves 256 candidates.
3. Run the eight lines from this repository to get the PIN. Zero guesses needed if the full MAC was read.
4. Open `http://tef668x.local/`, submit the PIN, receive a session.
5. Upload any firmware image. It runs.

**Impact.** Full and persistent code execution on a device on the victim's home network. The rate limit does not help, because no guessing is involved.

**CVSS 3.1.** `AV:A/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H` = **8.0 High**. Adjacent rather than network is the only thing holding it below critical.

**Note.** This is decision 14 in `DECISIONS.md`, which argues that deriving the PIN means a factory reset restores it without storing it. That property is real. What the decision does not account for is that the input is public and the algorithm is open source, so the output is public too. A per device random PIN generated at first boot and stored in NVS would fix it, at the cost of the factory reset property. **This one needs a decision, so it is not being changed unilaterally.**

**Fix options, in order of preference.**
1. Generate a random PIN with `esp_random()` at first boot, store it in NVS, show it on the About screen and on the serial banner. Factory reset generates a new one rather than restoring the old one.
2. Keep the MAC derivation, but mix in a per device salt generated at first boot and kept in a separate NVS namespace that a settings reset does not clear.
3. Keep it as is, and require the PIN to be changed before firmware upload is allowed.

### SEC-02 HIGH, A08 Software and Data Integrity Failures, CWE-494

**Firmware images are not authenticated.**

**File:** `src/net/web_update.cpp:355` and `src/net/ota_service.cpp:14`

**Description.** Both update paths call `Update.begin()` / `Update.write()` / `Update.end()`. That checks the ESP32 image magic byte and a checksum. Both are integrity checks against a corrupt transfer. Neither says anything about who produced the image. Secure Boot is not enabled, so the bootloader does not check a signature either.

**Attacker action.** Any client that gets past the PIN, which SEC-01 makes cheap, uploads an image that does whatever it likes: joins the attacker's network, relays traffic, or simply bricks the radio by writing both slots.

**Impact.** Arbitrary persistent code execution. Rollback does not help, because a hostile image passes the self check on purpose.

**CVSS 3.1.** `AV:A/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H` = **7.4 High** on its own. Chained with SEC-01 the privilege requirement disappears.

**Fix.** ESP32 Secure Boot v2 with signed images is the real answer, and it is a one way eFuse burn that must be decided before any radio ships. A cheaper step that fits the current design is the sha256 in the GitHub release manifest that `DECISIONS.md` already plans for a later phase, checked before `Update.end()`. That raises the bar for a remote attacker but does not stop one who can produce their own image.

### SEC-03 MEDIUM, A02 Cryptographic Failures, CWE-319

**The PIN and the session cookie travel in clear.**

**File:** `src/net/web_update.cpp:460`, the server is plain HTTP on port 80

**Attacker action.** On the open setup access point there is no link layer encryption at all, so anyone in range reads the PIN out of the `POST /auth` body and the session token out of the `Set-Cookie` header. On a WPA2 network, anyone already on that network can ARP spoof or sit on a mirrored port and read the same two values.

**Impact.** The PIN and an active session, which is SEC-01 without needing the MAC.

**CVSS 3.1.** `AV:A/AC:H/PR:N/UI:R/S:U/C:H/I:H/A:N` = **6.4 Medium**.

**Fix.** TLS on an ESP32 means a self signed certificate, a browser warning every time, and about 40 KB of heap the WROOM has to spare but the later LVGL phases may not. The honest position is that this is a LAN device and TLS is deferred, which is fine as long as SEC-01 is fixed so the PIN is actually a secret. Record the decision either way.

### SEC-04 MEDIUM, A05 Security Misconfiguration, CWE-1188

**The setup access point is open, and it accepts Wi-Fi credentials with no PIN.**

**File:** `src/net/wifi_manager.cpp:72` and `src/net/web_update.cpp:310`

**Description.** `WiFi.softAP(sApSsid)` is called with no passphrase. `requireAuth(true)` on `/wifi` lets the credentials form through without a PIN whenever the radio is in access point mode.

**Attacker action.** Wait for, or cause, a Wi-Fi failure. Deauthentication frames will do it, and the radio falls back to its access point on its own. Join `tef668x-setup-35B4`, open `http://192.168.4.1/`, and point the radio at an attacker controlled network. The radio joins it. The attacker now has LAN adjacency, and with SEC-01 the PIN.

**Impact.** Device relocated onto a hostile network, then fully compromised.

**CVSS 3.1.** `AV:A/AC:L/PR:N/UI:N/S:U/C:L/I:H/A:H` = **6.8 Medium**.

**This is a deliberate trade and it is the right one.** The alternative is a passphrase the user cannot be told, because at that moment they have no working network and this build has no screen. It is recorded here so that phase 4, which does have a screen, can show a one time AP passphrase and close it.

### SEC-05 MEDIUM, A04 Insecure Design, CWE-770

**One attacker can lock the owner out of the radio indefinitely.**

**File:** `src/net/web_update.cpp:22`, a single static `AccessPinGate`

**Description.** The gate is one struct for the whole endpoint, not one per client. `access_pin.h:63` documents it as being for one client, which is what the tests cover, but `web_update` keeps a single instance.

**Attacker action.** Send five wrong PINs. Wait 60 seconds. Repeat forever from a script. The owner can never sign in to change settings, upload firmware or reboot.

**Impact.** Permanent denial of the administrative path. The radio keeps working, and serial access recovers it, so this is availability of a function rather than of the device.

**CVSS 3.1.** `AV:A/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L` = **4.3 Medium**.

**Note.** `DECISIONS.md` says "five wrong attempts locks the endpoint for a minute", so the current behaviour matches the decision as written. Keying the gate by client IP is a small change and strictly better: a real owner is never locked out by someone else's guessing, and an attacker gains nothing because each source still gets five tries a minute.

### SEC-06 LOW, A01 Broken Access Control, CWE-613

**A session is not bound to the client that created it.**

**File:** `src/net/web_update.cpp:95`

**Description.** `signedIn()` compares the cookie to the single stored token and nothing else. There is no binding to the source IP or to a user agent.

**Attacker action.** Read the cookie off the wire, per SEC-03, and replay it from another machine for up to 30 minutes.

**Impact.** Session takeover, which yields the same access as the PIN.

**CVSS 3.1.** `AV:A/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H` = **6.8**, but scored **Low** here because it needs SEC-03 to be exploited first and adds nothing an attacker does not already have at that point.

**Fix.** Store the client IP alongside the token and compare it. Two lines, and it makes a stolen cookie useless from anywhere else.

---

### SEC-07 LOW, A01 Broken Access Control, CWE-352

**The state changing endpoints have no CSRF token.**

**File:** `src/net/web_update.cpp:470` to `:474`

**Description.** `/auth`, `/wifi`, `/update` and `/reboot` are all `POST` with no anti CSRF token. The defence in place is `SameSite=Strict` on the session cookie, set at `web_update.cpp:277`, which stops any cross site request from carrying it.

**Attacker action.** A cross site `POST` from a page the victim visits would not carry the cookie in any browser that honours `SameSite`, so `requireAuth` refuses. The one case that is not covered is `/wifi` in access point mode, which needs no auth at all by design, but a victim on that access point has no internet and so cannot be led to a hostile page.

**Impact.** None demonstrable on current browsers. Recorded because the defence rests entirely on one cookie attribute, which is not defence in depth.

**CVSS 3.1.** `AV:N/AC:H/PR:N/UI:R/S:U/C:N/I:L/A:L` = **3.1 Low**.

**Fix.** A per session token in a hidden form field, checked on every POST.

---

### SEC-08 LOW, A05 Security Misconfiguration

**No security headers on the pages that carry the forms.**

**File:** `src/net/web_update.cpp:190`, `pageHead()`

**Description.** No `Content-Security-Policy`, no `X-Frame-Options`, no `Cache-Control: no-store`. All the CSS is inline in the page, so a CSP is cheap to add and would be strict.

**Attacker action.** Clickjacking needs the victim signed in, the attacker to know the address, and the victim to visit a hostile page. Low likelihood, but the payoff is a firmware upload.

**CVSS 3.1.** `AV:N/AC:H/PR:N/UI:R/S:U/C:N/I:L/A:L` = **3.1 Low**.

**Fix.** Three `sendHeader` calls in `pageHead`: `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; form-action 'self'`, `X-Frame-Options: DENY`, `Cache-Control: no-store`.

### SEC-09 LOW, A04 Insecure Design, CWE-400

**An unauthenticated client can make the radio read a large request body.**

**File:** `src/net/web_update.cpp:340`

**Description.** The authorisation check happens at `UPLOAD_FILE_START`. A rejected upload sets `sUploadRejected` and returns, but the ESP32 `WebServer` still reads the rest of the body off the socket before the reply handler runs.

**Attacker action.** POST a 3 MB body with no PIN, repeatedly. Nothing is written to flash, and the reply is 403, but the radio spends the transfer time on it.

**Impact.** Slow denial of service against the web interface only. The radio itself stays up.

**CVSS 3.1.** `AV:A/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L` = **4.3**, scored **Low** because nothing is written and recovery is immediate.

## False positives noted

- **`/status.json` needs no PIN.** Deliberate, per the access PIN decision: viewing is open, changing is not.
- **`/wifi` needs no PIN in access point mode.** Deliberate, and it is the recovery path. Covered as SEC-04.
- **The PIN is printed over serial.** Serial needs physical access to the radio, which already beats every control here.
- **No `Update.setMD5()`.** The integrity of the transfer is covered by TCP and the image checksum. Authenticity is SEC-02, and an MD5 the uploader chooses would not add any.

## Phase 1 addendum, the build and CI surface

Phase 1 added no firmware logic. The changes are `.clang-format`, `Doxyfile`,
`tools/check.sh`, `.github/workflows/ci.yml`, doc comments, formatting and three
tests. The only new attack surface is the build pipeline, so that is what was
looked at. OWASP A08, Software and Data Integrity Failures, is the category that
applies.

Five things were found. Four were fixed before this was committed, and the
fifth was raised and settled as a decision. They are recorded because what was
done about them is the point, not the finding.

One of the five came from the code review rather than from this audit, which is
the two passes working as intended: the review reads for correctness and caught
a permissions rule that has a security consequence.

### CI-01, fixed. Script injection into the size report job

The first version of the workflow interpolated `${{ steps.head.outputs.report }}`
straight into an `actions/github-script` body. That content comes from the build
log of the branch being tested. A backtick or a `${` in a source file name would
have broken out of the template literal and run as JavaScript in a job holding
`pull-requests: write`.

Fixed by writing the numbers to a file and reading them with `fs.readFileSync`.
No `${{ }}` reaches a script body anywhere in the workflow.

### CI-02, fixed. A job that both ran branch code and could write

The size job checked out the pull request, ran `pio run`, and held
`pull-requests: write`. `pio run` executes `extra_scripts` from
`platformio.ini`, which is Python from the branch under test. A pull request
that edited `tools/pio_upload_port.py` would have run with that token.

Fork pull requests get a read only token, so this was not exploitable from
outside, but it was one setting away from being so.

Fixed by splitting it in three. `measure` checks out and builds with no write
permission and uploads the numbers as an artifact. `report` holds the write
permission, does no checkout at all, and only reads that artifact.

### CI-03, partly addressed by decision. Actions on moving major tags

The actions were several major versions behind: checkout on v5 when v7 is
current, github-script on v7 when v9 is current. All are now on their latest
major tag, which is what the dependency rule in CLAUDE.md asks for.

They are on tags, not commit SHAs. That was raised and decided on 12 September
2026: version numbers are easier to read and to keep current than forty
character hashes, and a file full of SHAs stops being updated.

The residual risk is real and worth stating. A major tag is a pointer the
action's owner can move, so a compromised release would run here with this
repository's token. Two things limit what that reaches. The workflow is read
only by default, and the one job holding `pull-requests: write` does no checkout
and runs nothing from the branch, so the worst a moved tag could do in that job
is post a wrong comment. Revisit this if the pipeline ever gains a secret or
permission to push.

### CI-04, fixed. Unpinned tool versions, and a formatter that disagreed with itself

`pip install platformio` and `apt-get install clang-format` take whatever is
current. That is the same supply chain problem as an unpinned library, and for
clang-format it was also a correctness bug: Ubuntu ships 18, macOS ships 21, and
a format gate that answers differently in two places is worse than no gate.

Fixed by pinning `platformio==6.1.19`, `gcovr==8.6` and `clang-format==23.1.1`,
and by making `tools/check.sh` refuse any clang-format that is not the pinned
version rather than quietly using a different one.

### CI-05, fixed. A job level permissions block that silently removed access

The reporting job listed only `pull-requests: write`. A job level `permissions`
block **replaces** the workflow level one rather than merging with it, so every
scope not named becomes `none`, not `read`. That job would have started with no
`contents` and no `actions` access at all and failed on the artifact download.

The failure mode is worth noting beyond this one job: the same mistake in the
other direction is how a job ends up with more access than intended, because
anyone reading it assumes the two blocks combine. Every scope the job needs is
now listed, with a comment saying why.

### Checked and clean

| Area | Result |
|---|---|
| Trigger choice | `pull_request`, not `pull_request_target`. Fork pull requests get no secrets and a read only token |
| Default permissions | `contents: read` at the workflow level, so a new job cannot inherit write by accident |
| `tools/check.sh` | No `eval`, no unquoted expansion of anything outside the repository, no network access |
| Cache poisoning | `actions/cache` restores the PlatformIO toolchain. GitHub scopes caches per branch, so a pull request cannot overwrite what `dev` restores |
| Secrets | None used, none needed. The workflow reads no secret at all |
| Artifact retention | Seven days for the doc build, one day for the size numbers |

### Still open from phase 1

CI-03 is accepted rather than closed: actions are on major version tags rather
than commit SHAs, by decision. The other three were fixed in the same change
that introduced them.

## Phase 2 addendum, the band plan

`core/band_plan.c` and its header. Pure arithmetic and one string formatter, no
network and no hardware, so the surface is memory safety and integer handling.
Nothing here is reachable from outside yet, which is the point of fixing it
now: #12 makes every one of these functions take a number from the network.
OWASP A03, Injection, does not apply. CWE-190 and CWE-787 do.

### BP-01, fixed. Integer overflow in the step arithmetic

`bandStepUp` computed `lo + ((freq - lo) / step + 1) * step` and then asked
whether the result was above the top edge. For a frequency near the top of a
`uint32_t` that multiplication wraps, and the wrapped value lands back **inside**
the band, so the check passed and the function returned it.

Demonstrated before the fix, on shortwave with a 5 kHz step:

```
lo=1700 hi=27000 step=5 freq=4294967295
computed next = 4, and next > hi is false
so bandStepUp returns 4 instead of wrapping to 1700
```

4 kHz is outside the band, off the channel grid, and below the tuner's range.
What the driver does when told to tune there is undefined, and it would have
been reached by `POST /api/tune` with a large number as soon as #12 lands.

Fixed by wrapping before the arithmetic rather than after it: a frequency at or
above the top edge returns the low edge, which is both the right answer and the
thing that keeps the multiplication bounded. `bandStepDown` already guarded its
subtraction the same way. A test now walks every band and every step size with
`UINT32_MAX` and with 0 and asserts the result is inside the band.

### Checked and clean

| Area | Result |
|---|---|
| `bandFormatFrequency` | The widest case is a ten digit `uint32_t` into a 24 byte buffer, and the result is length checked against the caller's buffer before the copy. No overflow. The AM format was grouped in threes when this was written, which made the widest case 13 characters; it is plain digits now, which is shorter |
| `bandStepDown` | Guards `freqKHz <= lo` and `freqKHz > hi` before subtracting, so the offset cannot underflow |
| `bandTopChannel` | `(hi - lo) / step * step` is bounded by the band width. No overflow |
| Table indexing | Every lookup goes through `validBand`, and the band, region and spacing tables are sized by their own enum count |
| Division | Every division by a step is behind `bandStepAllowed`, which refuses zero |
| Untrusted input | None yet. This layer has no caller from the network until #12, which is exactly why the overflow was worth fixing now rather than then |

### BP-02, fixed. Out pointers written without a NULL check

`bandForFrequency` wrote through its out pointer with no check, and
`bandPlanDefaults` and `bandLimits` did the same, while `bandFormatFrequency`
did check. An inconsistent contract on a `core/` API that the UI and the network
layer will both call is how a NULL from one caller becomes a crash nobody
expected. Every out pointer is checked now, and a test passes NULL to each.

Raised by the code review rather than by this audit.

### TU-03, fixed. A client input error reported as a server fault

This audit originally claimed no failure path returns a bare 500. That was not
true when it was written. `tef668xTuneFm` refuses any frequency that is not a
multiple of 10 kHz, which is the chip's tuning granularity, so `khz=87501`
passed the band check, came back as a range error, and the client was told
`500 The tuner refused it: out of range`.

A 500 says the radio is broken. Telling a caller that when they sent a number
the hardware cannot reach sends them looking in the wrong place, and on a
device whose whole recovery story is "reach it over HTTP" that matters more
than it would elsewhere. It now returns `400 The tuner cannot reach that. FM
tunes in steps of 10 kHz.`

Raised by the code review, which also noticed the audit was claiming otherwise.

### TU-04, fixed. Live readings published from a tuner that was never tuned

`/status.json` read the quality registers whether or not anything had been
tuned. If the tuner started but the boot tune failed, the reply left out the
band and frequency but still published a signal level, bandwidth and stereo
flag, all describing nothing. A reader has no way to tell that apart from a
real reading. The quality block is now omitted when nothing is tuned.

### Still open from phase 2

Nothing. All four were fixed in the change that introduced them.

## Phase 2 addendum, the tuner driver and the first API endpoint

`drivers/tef668x*`, and `POST /api/tune` in `net/web_update.cpp`. The driver
itself is not reachable from the network, but the endpoint is, and it is the
first thing that takes a number off the wire and hands it to the radio.

### TU-01, fixed. Stale capability set survived a failed restart

`tef668xBegin` never cleared `sReady` or `sCaps` on entry. A second call that
failed part way, say because the bus had gone, left the previous result in
place, so `tef668xCapabilities()` kept returning a working tuner and
`/status.json` kept reporting one. The error branch added specifically to
report the reason could never be reached.

That matters beyond tidiness: the whole point of reporting a tuner fault over
HTTP is that it can be seen without a serial cable, and this made the report
lie in exactly the case it exists for. Both are cleared on entry now.

Raised by the code review.

### TU-02, fixed. Unchecked multiplication in the bandwidth calls

`bandwidthKHz * 10` was cast to `uint16_t` with no range check, unlike the
volume and tune calls which both validate. Anything above 6553 kHz wrapped and
set a bandwidth the caller did not ask for. Both bandwidth calls now refuse
anything above 6000 kHz.

### Checked and clean

| Area | Result |
|---|---|
| `POST /api/tune` | Behind the PIN. The frequency is parsed, refused if not positive, and then has to fall inside a band from `core/band_plan.h` before it reaches the driver. A value too large to be a frequency is rejected by the band check, not by luck |
| Error replies | Every failure path returns a status code and a plain reason, and no 200 ever hides a dropped command |
| `writeBlob` | Chunks are capped at 24 into a 25 byte buffer |
| `command()` | Argument count capped at 6 into a 15 byte buffer |
| `query()` | Reads exactly the length the caller asked for, and every caller passes `sizeof` of its own buffer |
| Patch blobs | Byte for byte identical to the source they came from, confirmed by the code review: 6108, 118, 5754 and 128 bytes |
| Secrets | The driver holds none. The endpoint uses the existing session, and adds no new credential |

### A note that is not a finding

The driver now patches the tuner on every start rather than trusting the chip's
"already patched" answer. That was a correctness fix, not a security one, but it
has a security shape worth recording: after an update over the air the ESP32
reboots and the tuner does not, so anything the previous firmware put into the
tuner survives the update. A firmware update that was meant to change tuner
behaviour would silently not have done so. Trusting a peripheral's account of
its own state across an update is the general lesson.

# Phase 2 addendum, the HTTP control API

**Scope:** the nine `/api/*` routes in `net/web_update.cpp`, the shared state document `buildState`, and the command round trip in `radio_task.cpp`. Same threat model as above: an attacker on the same LAN as the radio, or within Wi-Fi range of it.

**Status:** no new Critical, High or Medium finding. Two accepted decisions and one note are recorded below.

The control API is decision 25 made real. Every command the radio can carry out is now reachable over HTTP. That is a deliberate widening of the write surface, so the question this addendum has to answer is whether the gate that was already there still covers all of it.

## The gate, checked route by route

| Route | Method | Gate | Result |
|---|---|---|---|
| `/api/state` | GET | none, on purpose | Open read. See API-01 |
| `/api/tune` | POST | `requireAuth(false)` | Behind the PIN |
| `/api/step` | POST | `requireAuth(false)` | Behind the PIN |
| `/api/band` | POST | `requireAuth(false)` | Behind the PIN |
| `/api/bandwidth` | POST | `requireAuth(false)` | Behind the PIN |
| `/api/step-size` | POST | `requireAuth(false)` | Behind the PIN |
| `/api/volume` | POST | `requireAuth(false)` | Behind the PIN |
| `/api/mute` | POST | `requireAuth(false)` | Behind the PIN |
| `/api/mode` | POST | `requireAuth(false)` | Behind the PIN |

Every write checks the session before it reads a single argument, so an unauthenticated request costs one string compare and a 403. Verified on the radio: all four write endpoints tested without a cookie returned `403 Enter the access PIN first.`

Nothing in the API reboots the radio, writes NVS, or touches the Wi-Fi credentials. `settingsNvsSave` is called from two places only, `/wifi` and `/setpin`, both of which were already gated and are unchanged. So the API adds no flash wear path: a caller hammering `/api/tune` writes nothing to NVS.

## API-01, accepted. The state document is open to read and says whether the PIN is still the default

`GET /api/state` and `GET /status.json` need no session. The document includes `defaultPin`, which is `true` while the access PIN is 000000, along with the IP address, free heap, uptime, which application slot is running, and everything the tuner is set to.

An attacker on the LAN can therefore sweep for radios still on the default PIN without making a single login attempt, which means the rate limit gate in `core/access_pin.c` never sees them coming.

**Accepted, not fixed.** The root page already carries the same warning in a red banner to any unauthenticated visitor, and that is on purpose: the owner has to see it without signing in. Hiding the same fact in the JSON while showing it in the HTML would not remove the disclosure, it would only make the two disagree. The real fix is the one already on the roadmap, which is to stop shipping a known default.

**Residual risk:** a scanner can list which radios on a network are still on 000000. Whoever leaves the default PIN set is one guess away in any case.

## API-02, accepted. A write blocks the calling task while the radio acts

`apiSubmit` waits for the radio task to carry the command out before it answers, up to `API_SETTLE_MS`, which is 500 ms. That wait is on the task that runs `loop()`, so while it is waiting nothing else in `loop()` runs: `wifiLoop`, `otaLoop`, `webLoop` and `rollbackTick` all share it.

The code review was right to call the first version of this out. The radio task only looked at its queue once per 100 ms poll, so every write really did stall the loop for most of a poll interval. The task now sleeps on the queue instead of on the clock, so it picks a command up in about a millisecond.

Measured on the radio afterwards, over Wi-Fi: a `GET /api/state`, which waits for nothing, takes 31 to 43 ms. A write that retunes takes 45 to 68 ms. The wait itself is therefore about 5 to 12 ms, and the rest is the HTTP round trip. The 500 ms ceiling is only reached if the tuner stops answering on I2C.

**Accepted.** The wait is behind the PIN, so an unauthenticated attacker cannot reach it. The radio task on core 0 keeps its cadence throughout, which is the thing that must not stall. Answering before the radio has acted was the defect this change exists to fix.

**Residual risk:** someone who has the PIN can slow the web interface down. They can also replace the firmware, so this is not the weakest thing they could do.

## Checked and clean

| Area | Result |
|---|---|
| CSRF | The session cookie is `HttpOnly; SameSite=Strict`. A form post from another origin carries no cookie and gets a 403. SEC-07 is unchanged: a token would be defence in depth, `SameSite` covers it today |
| Reflected input | No endpoint echoes a submitted value back. Error text names the argument, never its content, and every reply is `text/plain` |
| Injection | There is no interpreter, no database, no shell and no file path anywhere in the API. A request becomes a fixed size `RadioCommand` struct of integers and enums, and nothing else crosses into the radio task |
| Argument parsing | Every number goes through one helper with an explicit low and high bound before it is cast. Out of range, not a number, and missing are three different plain replies |
| Command validation | `radioWouldAccept` runs the same pure state machine the radio task runs, so a refusal is the radio's own answer rather than a second copy of the rules that could drift from it |
| Fail safe | A full queue answers 503 and a slow radio answers 202 with the state unchanged. Neither ever answers 200 for a command that was dropped |
| Secrets | `buildState` carries no PIN, no session token and no Wi-Fi credentials. The PIN is formatted in `handleRoot` into a local that is deliberately never sent |
| Auditing | Every accepted write prints one line to the serial log saying what it did, alongside the existing line for every wrong PIN and its source IP |
| Memory safety | The state document is built with `String` and three `snprintf` calls into local buffers of 72, 128 and 176 bytes, each given its own `sizeof`. No fixed buffer takes a caller supplied length |

## Raised by the code review, all fixed

The code review of this change found five defects. None was exploitable, and all five are fixed. They are recorded here because three of them are about a component reporting something untrue, which is the failure mode this project keeps finding.

### CR-01. A command the radio refused answered 200

`apiSubmit` judged a command with `radioWouldAccept` before sending it, against the last published state. For the five endpoints whose reply text is built from the request rather than from the result, a command the radio then refused still answered `200` with the text of what was asked for. Two clients, or one client after a 202, was enough: a `POST /api/step-size khz=9` that passed the check against a medium wave state was refused by the radio once a concurrent band change had moved it to FM, and the caller was told `200 step 9 kHz` while the step was 100.

Fixed by deleting the guess. The radio task now records what its own state machine made of each command, keyed by the ticket the caller holds, and `apiSubmit` reports that. There is one validation path, and it is the radio's. `radioWouldAccept` is gone.

### CR-02. The 202 path poisoned the next request

A command that was taken but not finished inside the wait left nothing to say it was outstanding, so the next request was validated against a state that predated it. Fixed by CR-01: there is no longer a check that runs ahead of the radio.

### CR-03. A failed publish stranded every later caller

The radio task applied commands and then published the count of them. If the publish could not take the lock, the count was lost for good, `applied` stayed permanently behind, and every later write answered 202 forever while the radio quietly kept working. It needs a broken mutex to happen and it cannot be recovered without a reboot. The task now carries an unpublished count forward to the next round.

### CR-04. Each write stalled the loop for most of a poll interval

See API-02 above.

### CR-05. The tune endpoint used its own copy of the band plan

`handleApiTune` worked out which band a frequency was in using `bandPlanDefaults`, while the radio task used the plan it was started with. They agree today because `main.cpp` passes the defaults. The moment the plan comes from settings, a medium wave spacing of 10 kHz or a different FM region moves the band edges, and the endpoint would name a band the radio was not on. The endpoint now asks the task for its plan.

## A note that is not a finding

The bug this change fixes has a security shape worth writing down. `radioWouldAccept` judged a command against the last published snapshot, which was up to 100 ms old. That was safe while a person turning a knob was the only source of commands, and the header said so. An HTTP API is a second source that can send commands faster than the radio publishes, and the check silently started answering about the state before the previous command. It refused things that were allowed, and reported frequencies the radio was not on.

Nothing was exploitable. The lesson is that a validity check against a cached copy of the state is only sound while the rate of change is bounded by something outside the attacker's control, and adding a network interface removes that bound. The check now runs against a state that has settled.

# Phase 2 addendum, the input layer

**Scope:** `core/input.c`, `drivers/encoder.cpp`, `drivers/keypad.cpp`, `drivers/i2c_bus.cpp`, `input_task.cpp`, the per band frequency memory and the cycle commands in `core/radio.c`, and the `input` field and `POST /api/cycle` in `net/web_update.cpp`. Same threat model: an attacker on the same LAN as the radio, or within Wi-Fi range of it.

**Status:** no new Critical, High or Medium finding. One accepted disclosure, and one availability note.

Physical input needs no PIN and never will. Whoever is holding the radio can already turn it off, so a gate on the knob would protect nothing and would lock the owner out of their own set. The PIN exists to stop someone on the network doing what only someone in the room should be able to do, and that boundary is unchanged.

## The gate

`POST /api/cycle` is a write and checks the session before it reads an argument, the same as the other eight. Verified on the radio: `403 Enter the access PIN first.` with no cookie. It carries no value from the caller at all, only which thing to move on, so there is nothing in it to range check beyond the four names it accepts.

## IN-01, accepted. The state document says what is being keyed at the radio

`GET /api/state` needs no session and now carries an `input` field: how many clicks and presses since boot, the last event in words, the digits keyed and not yet entered, and the raw state of the sixteen keypad lines.

So an unauthenticated caller on the LAN can watch, in near real time, that somebody is standing at the radio pressing buttons, and can read the frequency they are part way through typing.

**Accepted, not fixed.** What leaks is a frequency and the fact that a person is present. The same document already says what the radio is tuned to, which is the same information a moment later. Gating it would remove the one way to tell a dead switch from a wrong pin number on a radio that has no display yet, which is the whole reason the field exists.

**Residual risk:** somebody on the network learns that the radio is being used and what is being typed into it. Worth revisiting in phase 5 if the field survives past the display work.

## IN-02, note. One bus, two tasks

The tuner, the keypad and the clock share two pins. `drivers/i2c_bus.cpp` now serialises whole transactions, and the tuner holds the bus across a 2 ms settle after each write, five of those for a retune. A keypad read that arrives in the middle waits up to `I2C_BUS_WAIT_MS`, which is 100 ms, and then gives up rather than talking over the tuner.

This is not attacker reachable. No endpoint causes a keypad read, and the keypad is polled on a fixed 20 ms cadence whatever the network is doing. It is recorded because it is the first place where two tasks contend for one piece of hardware, and because the failure mode is silent by nature: see the finding below.

## IN-03, fixed. The bug worth writing down

Two tasks used the bus with no lock. That did not fail loudly. A tuner read is a write of the register wanted followed by a read of the answer, and a keypad transaction landing between the two returned zeros and reported success.

The result was a radio that read signal 0, bandwidth 0 and modulation 0 on shortwave, which is exactly what a dead band looks like. It was found only because an AM bandwidth of 0 is impossible: the filter is 4 kHz whether or not a station is there. Without that one impossible number it would have been put down to poor reception.

Three lessons, all of which have shown up before in this project:

1. A shared resource with no lock produces wrong data, not an error. Nothing in the logs said anything was wrong.
2. The failure imitated a legitimate condition. A quiet band and a broken read both read zero, which is the same shape as the stale snapshot problem in the control API, where a refused command and an accepted one both answered 200.
3. The tell was a value that could not physically occur. It is worth knowing, for every field published, which values are impossible.

## Checked and clean

| Area | Result |
|---|---|
| Injection | The `input` field is built from a fixed set of internal strings and from digits. Both go through `jsonEscape` anyway, so no value can break the document |
| Buffer safety | `sTyped` is nine bytes, capped at eight digits with the terminator at index eight. Every `snprintf` into the event text uses `sizeof` of its own buffer. The keypad line map is indexed 0 to 15 over a sixteen entry table |
| Command validation | The cycle commands take no value from the caller. The radio works out the next band, bandwidth or mode from its own state, which removed a class of bug rather than adding one |
| Fail safe | `i2cBusTake` refuses once the bus is started and no lock exists, rather than running unlocked. An unlocked bus returns plausible wrong data, which is worse than a read that fails |
| Physical input and the PIN | Input never posts a command a caller could not already send with the PIN. There is no privileged action reachable from the panel and not from the API |
| Secrets | Nothing in the input layer touches the PIN, the session or the Wi-Fi credentials |

# Phase 2 addendum, the display

**Scope:** `drivers/display.cpp`, `ui/screen.cpp`, `ui/font.h` and the two generated fonts, `screen_task.cpp`, and `tools/make_font.py`. Same threat model.

**Status:** no finding at any severity. The display is an output with no input, which is why this section is short, and the reasoning for that is worth stating rather than leaving as an assumption.

## Why there is almost no attack surface here

Nothing reaches the panel from the network. `screen_task.cpp` reads a snapshot of the radio's state and turns it into strings; every one of those is either a number the radio measured or a pointer to a string literal chosen by a switch. No text a caller supplies, over HTTP or otherwise, is ever drawn. The nearest thing is the Wi-Fi network name, and that goes to the web page, not to the panel.

Nothing is read back from the panel either. SPI is write only here, MISO is not attached, and no code path turns pixels back into data. So there is no parser and nothing to confuse.

| Area | Result |
|---|---|
| Buffer safety, glyphs | `sGlyph` is 64 by 40. `displayText` refuses a font taller than 40 and clamps the width to 64, so the largest index written is `height * w - 1`, inside the array. The two fonts are 12 and 22 pixels wide and 18 and 31 tall, so neither limit is reached |
| Buffer safety, font data | Checked the arrays against their own tables. The small font is 2124 bytes and its last glyph ends at exactly 2124; the large font is 1054 and ends at 1054. No read past either |
| Generated code | The generator now refuses to emit a font whose glyph offsets would not fit the `uint16_t` they are stored in, rather than wrapping silently, and exits non zero when it fails |
| Rectangles | `displayFill` clips to the panel through a signed intermediate, so a negative position cannot wrap into a huge unsigned window. `displayPush` refuses an off panel rectangle outright rather than drawing part of it |
| Strings | Every `snprintf` uses `sizeof` of its own buffer. The remembered lines are 64 bytes, longer than the longest string any field can hold, which was not true at first and made one field redraw itself for ever |
| Concurrency | `radioGetSnapshot` copies under the lock and releases it before anything is drawn. No lock is held across SPI. The panel is only ever touched from the loop task |
| Availability | A full screen clear is the most expensive thing here, and the loop task does not run while it happens. It is now a burst write rather than a byte at a time, and the redundant clears at start up were removed. Not reachable from the network in any case |

## A note that is not a finding

The SPI bus transaction was held open for the life of the firmware. That is not a security problem today, because nothing else uses the bus, but it is a deadlock waiting for phase 4: the touch controller shares the bus, needs a slower clock, and would have blocked for ever on the semaphore with no timeout. It now takes and gives the bus per operation.

Worth recording next to the I2C finding above, because it is the same shape. Both are a shared piece of hardware with no arbitration, and in both cases the failure is silence rather than an error.

# Phase 2 addendum, the reception defaults

**Scope:** `applyReceptionDefaults` in `drivers/tef668x.cpp`, nineteen configuration writes to the tuner at start up. Same threat model.

**Status:** no finding. Recorded because "no finding" is worth writing down with the reason, not left as an assumption.

There is no input here. Every value is a compile time constant, the sequence runs once during start up before the network is up, and nothing about it can be influenced by a request, a person at the radio, or anything on the air. No buffer takes a caller supplied length: the argument array is sized to what the command helper accepts rather than to what this function passes, so a longer command added later cannot read past its end.

| Area | Result |
|---|---|
| Input | None. Nineteen writes of fixed values, no parameter from anywhere |
| Reachability | Start up only, before Wi-Fi, before the web server |
| Memory safety | `args` is sized to the helper's maximum, not to current use |
| Availability | A failure is reported and start up continues. These are quality writes, and refusing to start would turn a radio that sounds wrong into a radio that does not work, which is worse and which the owner cannot fix from where they are standing |
| Correctness | Every write was checked against the reference firmware's source: module, command number, argument count and value. All nineteen match |

## Worth recording, because it nearly went in wrong

The values were all correct. Two of the comments describing them were not: they said the stereo blend and the treble roll off were being switched on, when mode 0 in both cases switches them off. The reference firmware ships with both off, so the code was right and the explanation was inverted.

That is a documentation defect rather than a security one, and it is in this file because of what it would have cost. Someone reading "a weak station goes to mono rather than hissing in stereo" and hearing hiss would go looking for a fault in the blend, which was never on. A wrong comment next to a right value survives review longer than a wrong value does, because the code keeps working.
