# Security audit report, 2026-09-12

**Overall status:** YELLOW
**Scope:** phase 0, `src/` and `platformio.ini` and `partitions.csv`. Phase 1 adds the build and CI surface, covered in its own section below.
**Standards:** OWASP Top 10 2021, OWASP ASVS L1 and L2, CWE, CVSS v3.1
**Threat model:** the attacker is on the same LAN as the radio, or within Wi-Fi range of it. There is no internet exposure. The radio serves plain HTTP on port 80 and accepts firmware uploads.

The OWASP checklists are written against web applications. This is ESP32 firmware in C and C++, so each category was translated rather than dropped. Where a control has no meaning here, that is said rather than left blank.

---

## Executive summary

| Severity | Count |
|---|---|
| Critical | 0 |
| High | 1 (1 resolved) |
| Medium | 3 |
| Low | 4 |
| Info | 3 |

**The three to fix first**

1. ~~**SEC-01.** The default access PIN is computed from the MAC address.~~ **Resolved.** The default is now 000000 with a warning on boot and on the page.
2. **SEC-02.** Firmware images are not authenticated. `Update` checks the ESP32 image magic and a checksum, which is integrity against corruption, not proof of origin. Anyone past the PIN can run any code they like on the radio, permanently.
3. **SEC-03.** Everything, including the PIN and the session cookie, travels in clear over HTTP. On the setup access point, which is open, every frame is readable by anyone in range.

**What is already right**

- No third party libraries at all. The only dependency is the Arduino ESP32 core, pinned to an exact version.
- Session tokens come from `esp_random`, which is the hardware RNG, and are compared in constant time.
- The session cookie is `HttpOnly` and `SameSite=Strict`.
- Network names are HTML escaped before being put in the page, so a hostile SSID cannot inject markup.
- The PIN attempt gate and its lockout are wrap safe across the 49 day millisecond rollover, and that is covered by a test.
- Every buffer write uses `snprintf` or a bounds checked copy. No `strcpy`, `sprintf` or `strcat` anywhere.
- The PIN is never sent to the browser.

## Findings

### SEC-01 RESOLVED, was HIGH, A07 Identification and Authentication Failures, CWE-340

**Resolved on 12 September 2026.** The MAC derivation was dropped. The default
PIN is now 000000, and a radio still on it warns on every boot and shows a red
banner on its own web page. The default is still not a secret, but it no longer
pretends to be one, and the user is told plainly to change it. Decision 12 in
`DECISIONS.md` was rewritten to match.

The original finding follows, for the record.

**The default access PIN is computable by anyone who can see the radio.**

**File:** `src/core/access_pin.c:12`, used from `src/main.cpp:88` and `src/net/web_update.cpp`

**Description.** `accessPinFromMac()` is FNV-1a over the six MAC bytes, modulo one million. The algorithm is eight lines of GPL source in a public repository. The MAC is not a secret: it is in the header of every 802.11 frame the radio sends, in clear, even on a WPA2 network, and `arp -a` returns it to anything on the LAN. `board_ats125.h:19` also puts the last two MAC bytes into the setup access point SSID.

**Attacker action.**
1. Sit within radio range, or on the same LAN.
2. Read the MAC. From the LAN, `arp -a` after one ping. From the air, any captured frame header, or the AP SSID plus the Espressif OUI leaves 256 candidates.
3. Run the eight lines from this repository to get the PIN. Zero guesses needed if the full MAC was read.
4. Open `http://tef668x.local/`, submit the PIN, receive a session.
5. Upload any firmware image. It runs.

**Impact.** Full and persistent code execution on a device on the victim's home network. The rate limit does not help, because no guessing is involved.

**CVSS 3.1.** `AV:A/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H` = **8.0 High**. Adjacent rather than network is the only thing holding it below critical.

**Note.** This is decision 12 in `DECISIONS.md`, which argues that deriving the PIN means a factory reset restores it without storing it. That property is real. What the decision does not account for is that the input is public and the algorithm is open source, so the output is public too. A per device random PIN generated at first boot and stored in NVS would fix it, at the cost of the factory reset property. **This one needs a decision, so it is not being changed unilaterally.**

**Fix options, in order of preference.**
1. Generate a random PIN with `esp_random()` at first boot, store it in NVS, show it on the About screen and on the serial banner. Factory reset generates a new one rather than restoring the old one.
2. Keep the MAC derivation, but mix in a per device salt generated at first boot and kept in a separate NVS namespace that a settings reset does not clear.
3. Keep it as is, and require the PIN to be changed before firmware upload is allowed.

### SEC-02 HIGH, A08 Software and Data Integrity Failures, CWE-494

**Firmware images are not authenticated.**

**File:** `src/net/web_update.cpp:355` and `src/net/ota_service.cpp:14`

**Description.** Both update paths call `Update.begin()` / `Update.write()` / `Update.end()`. That checks the ESP32 image magic byte and a checksum. Both are integrity checks against a corrupt transfer. Neither says anything about who produced the image. Secure Boot is not enabled, so the bootloader does not check a signature either.

**Attacker action.** Any client that gets past the PIN, which SEC-01 makes cheap, uploads an image that does whatever it likes: joins the attacker's network, relays traffic, or simply bricks the radio by writing both slots.

**Impact.** Arbitrary persistent code execution. Rollback does not help, because a hostile image passes the self check on purpose.

**CVSS 3.1.** `AV:A/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H` = **7.4 High** on its own. Chained with SEC-01 the privilege requirement disappears.

**Fix.** ESP32 Secure Boot v2 with signed images is the real answer, and it is a one way eFuse burn that must be decided before any radio ships. A cheaper step that fits the current design is the sha256 in the GitHub release manifest that `DECISIONS.md` already plans for a later phase, checked before `Update.end()`. That raises the bar for a remote attacker but does not stop one who can produce their own image.

### SEC-03 MEDIUM, A02 Cryptographic Failures, CWE-319

**The PIN and the session cookie travel in clear.**

**File:** `src/net/web_update.cpp:460`, the server is plain HTTP on port 80

**Attacker action.** On the open setup access point there is no link layer encryption at all, so anyone in range reads the PIN out of the `POST /auth` body and the session token out of the `Set-Cookie` header. On a WPA2 network, anyone already on that network can ARP spoof or sit on a mirrored port and read the same two values.

**Impact.** The PIN and an active session, which is SEC-01 without needing the MAC.

**CVSS 3.1.** `AV:A/AC:H/PR:N/UI:R/S:U/C:H/I:H/A:N` = **6.4 Medium**.

**Fix.** TLS on an ESP32 means a self signed certificate, a browser warning every time, and about 40 KB of heap the WROOM has to spare but the later LVGL phases may not. The honest position is that this is a LAN device and TLS is deferred, which is fine as long as SEC-01 is fixed so the PIN is actually a secret. Record the decision either way.

### SEC-04 MEDIUM, A05 Security Misconfiguration, CWE-1188

**The setup access point is open, and it accepts Wi-Fi credentials with no PIN.**

**File:** `src/net/wifi_manager.cpp:72` and `src/net/web_update.cpp:310`

**Description.** `WiFi.softAP(sApSsid)` is called with no passphrase. `requireAuth(true)` on `/wifi` lets the credentials form through without a PIN whenever the radio is in access point mode.

**Attacker action.** Wait for, or cause, a Wi-Fi failure. Deauthentication frames will do it, and the radio falls back to its access point on its own. Join `tef668x-setup-35B4`, open `http://192.168.4.1/`, and point the radio at an attacker controlled network. The radio joins it. The attacker now has LAN adjacency, and with SEC-01 the PIN.

**Impact.** Device relocated onto a hostile network, then fully compromised.

**CVSS 3.1.** `AV:A/AC:L/PR:N/UI:N/S:U/C:L/I:H/A:H` = **6.8 Medium**.

**This is a deliberate trade and it is the right one.** The alternative is a passphrase the user cannot be told, because at that moment they have no working network and this build has no screen. It is recorded here so that phase 4, which does have a screen, can show a one time AP passphrase and close it.

### SEC-05 MEDIUM, A04 Insecure Design, CWE-770

**One attacker can lock the owner out of the radio indefinitely.**

**File:** `src/net/web_update.cpp:22`, a single static `AccessPinGate`

**Description.** The gate is one struct for the whole endpoint, not one per client. `access_pin.h:63` documents it as being for one client, which is what the tests cover, but `web_update` keeps a single instance.

**Attacker action.** Send five wrong PINs. Wait 60 seconds. Repeat forever from a script. The owner can never sign in to change settings, upload firmware or reboot.

**Impact.** Permanent denial of the administrative path. The radio keeps working, and serial access recovers it, so this is availability of a function rather than of the device.

**CVSS 3.1.** `AV:A/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L` = **4.3 Medium**.

**Note.** `DECISIONS.md` says "five wrong attempts locks the endpoint for a minute", so the current behaviour matches the decision as written. Keying the gate by client IP is a small change and strictly better: a real owner is never locked out by someone else's guessing, and an attacker gains nothing because each source still gets five tries a minute.

### SEC-06 LOW, A01 Broken Access Control, CWE-613

**A session is not bound to the client that created it.**

**File:** `src/net/web_update.cpp:95`

**Description.** `signedIn()` compares the cookie to the single stored token and nothing else. There is no binding to the source IP or to a user agent.

**Attacker action.** Read the cookie off the wire, per SEC-03, and replay it from another machine for up to 30 minutes.

**Impact.** Session takeover, which yields the same access as the PIN.

**CVSS 3.1.** `AV:A/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H` = **6.8**, but scored **Low** here because it needs SEC-03 to be exploited first and adds nothing an attacker does not already have at that point.

**Fix.** Store the client IP alongside the token and compare it. Two lines, and it makes a stolen cookie useless from anywhere else.

---

### SEC-07 LOW, A01 Broken Access Control, CWE-352

**The state changing endpoints have no CSRF token.**

**File:** `src/net/web_update.cpp:470` to `:474`

**Description.** `/auth`, `/wifi`, `/update` and `/reboot` are all `POST` with no anti CSRF token. The defence in place is `SameSite=Strict` on the session cookie, set at `web_update.cpp:277`, which stops any cross site request from carrying it.

**Attacker action.** A cross site `POST` from a page the victim visits would not carry the cookie in any browser that honours `SameSite`, so `requireAuth` refuses. The one case that is not covered is `/wifi` in access point mode, which needs no auth at all by design, but a victim on that access point has no internet and so cannot be led to a hostile page.

**Impact.** None demonstrable on current browsers. Recorded because the defence rests entirely on one cookie attribute, which is not defence in depth.

**CVSS 3.1.** `AV:N/AC:H/PR:N/UI:R/S:U/C:N/I:L/A:L` = **3.1 Low**.

**Fix.** A per session token in a hidden form field, checked on every POST.

---

### SEC-08 LOW, A05 Security Misconfiguration

**No security headers on the pages that carry the forms.**

**File:** `src/net/web_update.cpp:190`, `pageHead()`

**Description.** No `Content-Security-Policy`, no `X-Frame-Options`, no `Cache-Control: no-store`. All the CSS is inline in the page, so a CSP is cheap to add and would be strict.

**Attacker action.** Clickjacking needs the victim signed in, the attacker to know the address, and the victim to visit a hostile page. Low likelihood, but the payoff is a firmware upload.

**CVSS 3.1.** `AV:N/AC:H/PR:N/UI:R/S:U/C:N/I:L/A:L` = **3.1 Low**.

**Fix.** Three `sendHeader` calls in `pageHead`: `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; form-action 'self'`, `X-Frame-Options: DENY`, `Cache-Control: no-store`.

### SEC-09 LOW, A04 Insecure Design, CWE-400

**An unauthenticated client can make the radio read a large request body.**

**File:** `src/net/web_update.cpp:340`

**Description.** The authorisation check happens at `UPLOAD_FILE_START`. A rejected upload sets `sUploadRejected` and returns, but the ESP32 `WebServer` still reads the rest of the body off the socket before the reply handler runs.

**Attacker action.** POST a 3 MB body with no PIN, repeatedly. Nothing is written to flash, and the reply is 403, but the radio spends the transfer time on it.

**Impact.** Slow denial of service against the web interface only. The radio itself stays up.

**CVSS 3.1.** `AV:A/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:L` = **4.3**, scored **Low** because nothing is written and recovery is immediate.

## False positives noted

- **`/status.json` needs no PIN.** Deliberate, per the access PIN decision: viewing is open, changing is not.
- **`/wifi` needs no PIN in access point mode.** Deliberate, and it is the recovery path. Covered as SEC-04.
- **The PIN is printed over serial.** Serial needs physical access to the radio, which already beats every control here.
- **No `Update.setMD5()`.** The integrity of the transfer is covered by TCP and the image checksum. Authenticity is SEC-02, and an MD5 the uploader chooses would not add any.

## Phase 1 addendum, the build and CI surface

Phase 1 added no firmware logic. The changes are `.clang-format`, `Doxyfile`,
`tools/check.sh`, `.github/workflows/ci.yml`, doc comments, formatting and three
tests. The only new attack surface is the build pipeline, so that is what was
looked at. OWASP A08, Software and Data Integrity Failures, is the category that
applies.

Five things were found. Four were fixed before this was committed, and the
fifth was raised and settled as a decision. They are recorded because what was
done about them is the point, not the finding.

One of the five came from the code review rather than from this audit, which is
the two passes working as intended: the review reads for correctness and caught
a permissions rule that has a security consequence.

### CI-01, fixed. Script injection into the size report job

The first version of the workflow interpolated `${{ steps.head.outputs.report }}`
straight into an `actions/github-script` body. That content comes from the build
log of the branch being tested. A backtick or a `${` in a source file name would
have broken out of the template literal and run as JavaScript in a job holding
`pull-requests: write`.

Fixed by writing the numbers to a file and reading them with `fs.readFileSync`.
No `${{ }}` reaches a script body anywhere in the workflow.

### CI-02, fixed. A job that both ran branch code and could write

The size job checked out the pull request, ran `pio run`, and held
`pull-requests: write`. `pio run` executes `extra_scripts` from
`platformio.ini`, which is Python from the branch under test. A pull request
that edited `tools/pio_upload_port.py` would have run with that token.

Fork pull requests get a read only token, so this was not exploitable from
outside, but it was one setting away from being so.

Fixed by splitting it in three. `measure` checks out and builds with no write
permission and uploads the numbers as an artifact. `report` holds the write
permission, does no checkout at all, and only reads that artifact.

### CI-03, partly addressed by decision. Actions on moving major tags

The actions were several major versions behind: checkout on v5 when v7 is
current, github-script on v7 when v9 is current. All are now on their latest
major tag, which is what the dependency rule in CLAUDE.md asks for.

They are on tags, not commit SHAs. That was raised and decided on 12 September
2026: version numbers are easier to read and to keep current than forty
character hashes, and a file full of SHAs stops being updated.

The residual risk is real and worth stating. A major tag is a pointer the
action's owner can move, so a compromised release would run here with this
repository's token. Two things limit what that reaches. The workflow is read
only by default, and the one job holding `pull-requests: write` does no checkout
and runs nothing from the branch, so the worst a moved tag could do in that job
is post a wrong comment. Revisit this if the pipeline ever gains a secret or
permission to push.

### CI-04, fixed. Unpinned tool versions, and a formatter that disagreed with itself

`pip install platformio` and `apt-get install clang-format` take whatever is
current. That is the same supply chain problem as an unpinned library, and for
clang-format it was also a correctness bug: Ubuntu ships 18, macOS ships 21, and
a format gate that answers differently in two places is worse than no gate.

Fixed by pinning `platformio==6.1.19`, `gcovr==8.6` and `clang-format==23.1.1`,
and by making `tools/check.sh` refuse any clang-format that is not the pinned
version rather than quietly using a different one.

### CI-05, fixed. A job level permissions block that silently removed access

The reporting job listed only `pull-requests: write`. A job level `permissions`
block **replaces** the workflow level one rather than merging with it, so every
scope not named becomes `none`, not `read`. That job would have started with no
`contents` and no `actions` access at all and failed on the artifact download.

The failure mode is worth noting beyond this one job: the same mistake in the
other direction is how a job ends up with more access than intended, because
anyone reading it assumes the two blocks combine. Every scope the job needs is
now listed, with a comment saying why.

### Checked and clean

| Area | Result |
|---|---|
| Trigger choice | `pull_request`, not `pull_request_target`. Fork pull requests get no secrets and a read only token |
| Default permissions | `contents: read` at the workflow level, so a new job cannot inherit write by accident |
| `tools/check.sh` | No `eval`, no unquoted expansion of anything outside the repository, no network access |
| Cache poisoning | `actions/cache` restores the PlatformIO toolchain. GitHub scopes caches per branch, so a pull request cannot overwrite what `dev` restores |
| Secrets | None used, none needed. The workflow reads no secret at all |
| Artifact retention | Seven days for the doc build, one day for the size numbers |

### Still open from phase 1

CI-03 is accepted rather than closed: actions are on major version tags rather
than commit SHAs, by decision. The other three were fixed in the same change
that introduced them.

## Phase 2 addendum, the band plan

`core/band_plan.c` and its header. Pure arithmetic and one string formatter, no
network and no hardware, so the surface is memory safety and integer handling.
Nothing here is reachable from outside yet, which is the point of fixing it
now: #12 makes every one of these functions take a number from the network.
OWASP A03, Injection, does not apply. CWE-190 and CWE-787 do.

### BP-01, fixed. Integer overflow in the step arithmetic

`bandStepUp` computed `lo + ((freq - lo) / step + 1) * step` and then asked
whether the result was above the top edge. For a frequency near the top of a
`uint32_t` that multiplication wraps, and the wrapped value lands back **inside**
the band, so the check passed and the function returned it.

Demonstrated before the fix, on shortwave with a 5 kHz step:

```
lo=1700 hi=27000 step=5 freq=4294967295
computed next = 4, and next > hi is false
so bandStepUp returns 4 instead of wrapping to 1700
```

4 kHz is outside the band, off the channel grid, and below the tuner's range.
What the driver does when told to tune there is undefined, and it would have
been reached by `POST /api/tune` with a large number as soon as #12 lands.

Fixed by wrapping before the arithmetic rather than after it: a frequency at or
above the top edge returns the low edge, which is both the right answer and the
thing that keeps the multiplication bounded. `bandStepDown` already guarded its
subtraction the same way. A test now walks every band and every step size with
`UINT32_MAX` and with 0 and asserts the result is inside the band.

### Checked and clean

| Area | Result |
|---|---|
| `bandFormatFrequency` | The widest case is a ten digit `uint32_t` into a 24 byte buffer, and the result is length checked against the caller's buffer before the copy. No overflow. The AM format was grouped in threes when this was written, which made the widest case 13 characters; it is plain digits now, which is shorter |
| `bandStepDown` | Guards `freqKHz <= lo` and `freqKHz > hi` before subtracting, so the offset cannot underflow |
| `bandTopChannel` | `(hi - lo) / step * step` is bounded by the band width. No overflow |
| Table indexing | Every lookup goes through `validBand`, and the band, region and spacing tables are sized by their own enum count |
| Division | Every division by a step is behind `bandStepAllowed`, which refuses zero |
| Untrusted input | None yet. This layer has no caller from the network until #12, which is exactly why the overflow was worth fixing now rather than then |

### BP-02, fixed. Out pointers written without a NULL check

`bandForFrequency` wrote through its out pointer with no check, and
`bandPlanDefaults` and `bandLimits` did the same, while `bandFormatFrequency`
did check. An inconsistent contract on a `core/` API that the UI and the network
layer will both call is how a NULL from one caller becomes a crash nobody
expected. Every out pointer is checked now, and a test passes NULL to each.

Raised by the code review rather than by this audit.

### TU-03, fixed. A client input error reported as a server fault

This audit originally claimed no failure path returns a bare 500. That was not
true when it was written. `tef668xTuneFm` refuses any frequency that is not a
multiple of 10 kHz, which is the chip's tuning granularity, so `khz=87501`
passed the band check, came back as a range error, and the client was told
`500 The tuner refused it: out of range`.

A 500 says the radio is broken. Telling a caller that when they sent a number
the hardware cannot reach sends them looking in the wrong place, and on a
device whose whole recovery story is "reach it over HTTP" that matters more
than it would elsewhere. It now returns `400 The tuner cannot reach that. FM
tunes in steps of 10 kHz.`

Raised by the code review, which also noticed the audit was claiming otherwise.

### TU-04, fixed. Live readings published from a tuner that was never tuned

`/status.json` read the quality registers whether or not anything had been
tuned. If the tuner started but the boot tune failed, the reply left out the
band and frequency but still published a signal level, bandwidth and stereo
flag, all describing nothing. A reader has no way to tell that apart from a
real reading. The quality block is now omitted when nothing is tuned.

### Still open from phase 2

Nothing. All four were fixed in the change that introduced them.

## Phase 2 addendum, the tuner driver and the first API endpoint

`drivers/tef668x*`, and `POST /api/tune` in `net/web_update.cpp`. The driver
itself is not reachable from the network, but the endpoint is, and it is the
first thing that takes a number off the wire and hands it to the radio.

### TU-01, fixed. Stale capability set survived a failed restart

`tef668xBegin` never cleared `sReady` or `sCaps` on entry. A second call that
failed part way, say because the bus had gone, left the previous result in
place, so `tef668xCapabilities()` kept returning a working tuner and
`/status.json` kept reporting one. The error branch added specifically to
report the reason could never be reached.

That matters beyond tidiness: the whole point of reporting a tuner fault over
HTTP is that it can be seen without a serial cable, and this made the report
lie in exactly the case it exists for. Both are cleared on entry now.

Raised by the code review.

### TU-02, fixed. Unchecked multiplication in the bandwidth calls

`bandwidthKHz * 10` was cast to `uint16_t` with no range check, unlike the
volume and tune calls which both validate. Anything above 6553 kHz wrapped and
set a bandwidth the caller did not ask for. Both bandwidth calls now refuse
anything above 6000 kHz.

### Checked and clean

| Area | Result |
|---|---|
| `POST /api/tune` | Behind the PIN. The frequency is parsed, refused if not positive, and then has to fall inside a band from `core/band_plan.h` before it reaches the driver. A value too large to be a frequency is rejected by the band check, not by luck |
| Error replies | Every failure path returns a status code and a plain reason, and no 200 ever hides a dropped command |
| `writeBlob` | Chunks are capped at 24 into a 25 byte buffer |
| `command()` | Argument count capped at 6 into a 15 byte buffer |
| `query()` | Reads exactly the length the caller asked for, and every caller passes `sizeof` of its own buffer |
| Patch blobs | Byte for byte identical to the source they came from, confirmed by the code review: 6108, 118, 5754 and 128 bytes |
| Secrets | The driver holds none. The endpoint uses the existing session, and adds no new credential |

### A note that is not a finding

The driver now patches the tuner on every start rather than trusting the chip's
"already patched" answer. That was a correctness fix, not a security one, but it
has a security shape worth recording: after an update over the air the ESP32
reboots and the tuner does not, so anything the previous firmware put into the
tuner survives the update. A firmware update that was meant to change tuner
behaviour would silently not have done so. Trusting a peripheral's account of
its own state across an update is the general lesson.

# Phase 2 addendum, the HTTP control API

**Scope:** the nine `/api/*` routes in `net/web_update.cpp`, the shared state document `buildState`, and the command round trip in `radio_task.cpp`. Same threat model as above: an attacker on the same LAN as the radio, or within Wi-Fi range of it.

**Status:** no new Critical, High or Medium finding. Two accepted decisions and one note are recorded below.

The control API is decision 25 made real. Every command the radio can carry out is now reachable over HTTP. That is a deliberate widening of the write surface, so the question this addendum has to answer is whether the gate that was already there still covers all of it.

## The gate, checked route by route

| Route | Method | Gate | Result |
|---|---|---|---|
| `/api/state` | GET | none, on purpose | Open read. See API-01 |
| `/api/tune` | POST | `requireAuth(false)` | Behind the PIN |
| `/api/step` | POST | `requireAuth(false)` | Behind the PIN |
| `/api/band` | POST | `requireAuth(false)` | Behind the PIN |
| `/api/bandwidth` | POST | `requireAuth(false)` | Behind the PIN |
| `/api/step-size` | POST | `requireAuth(false)` | Behind the PIN |
| `/api/volume` | POST | `requireAuth(false)` | Behind the PIN |
| `/api/mute` | POST | `requireAuth(false)` | Behind the PIN |
| `/api/mode` | POST | `requireAuth(false)` | Behind the PIN |

Every write checks the session before it reads a single argument, so an unauthenticated request costs one string compare and a 403. Verified on the radio: all four write endpoints tested without a cookie returned `403 Enter the access PIN first.`

Nothing in the API reboots the radio, writes NVS, or touches the Wi-Fi credentials. `settingsNvsSave` is called from two places only, `/wifi` and `/setpin`, both of which were already gated and are unchanged. So the API adds no flash wear path: a caller hammering `/api/tune` writes nothing to NVS.

## API-01, accepted. The state document is open to read and says whether the PIN is still the default

`GET /api/state` and `GET /status.json` need no session. The document includes `defaultPin`, which is `true` while the access PIN is 000000, along with the IP address, free heap, uptime, which application slot is running, and everything the tuner is set to.

An attacker on the LAN can therefore sweep for radios still on the default PIN without making a single login attempt, which means the rate limit gate in `core/access_pin.c` never sees them coming.

**Accepted, not fixed.** The root page already carries the same warning in a red banner to any unauthenticated visitor, and that is on purpose: the owner has to see it without signing in. Hiding the same fact in the JSON while showing it in the HTML would not remove the disclosure, it would only make the two disagree. The real fix is the one already on the roadmap, which is to stop shipping a known default.

**Residual risk:** a scanner can list which radios on a network are still on 000000. Whoever leaves the default PIN set is one guess away in any case.

## API-02, accepted. A write blocks the calling task while the radio acts

`apiSubmit` waits for the radio task to carry the command out before it answers, up to `API_SETTLE_MS`, which is 500 ms. That wait is on the task that runs `loop()`, so while it is waiting nothing else in `loop()` runs: `wifiLoop`, `otaLoop`, `webLoop` and `rollbackTick` all share it.

The code review was right to call the first version of this out. The radio task only looked at its queue once per 100 ms poll, so every write really did stall the loop for most of a poll interval. The task now sleeps on the queue instead of on the clock, so it picks a command up in about a millisecond.

Measured on the radio afterwards, over Wi-Fi: a `GET /api/state`, which waits for nothing, takes 31 to 43 ms. A write that retunes takes 45 to 68 ms. The wait itself is therefore about 5 to 12 ms, and the rest is the HTTP round trip. The 500 ms ceiling is only reached if the tuner stops answering on I2C.

**Accepted.** The wait is behind the PIN, so an unauthenticated attacker cannot reach it. The radio task on core 0 keeps its cadence throughout, which is the thing that must not stall. Answering before the radio has acted was the defect this change exists to fix.

**Residual risk:** someone who has the PIN can slow the web interface down. They can also replace the firmware, so this is not the weakest thing they could do.

## Checked and clean

| Area | Result |
|---|---|
| CSRF | The session cookie is `HttpOnly; SameSite=Strict`. A form post from another origin carries no cookie and gets a 403. SEC-07 is unchanged: a token would be defence in depth, `SameSite` covers it today |
| Reflected input | No endpoint echoes a submitted value back. Error text names the argument, never its content, and every reply is `text/plain` |
| Injection | There is no interpreter, no database, no shell and no file path anywhere in the API. A request becomes a fixed size `RadioCommand` struct of integers and enums, and nothing else crosses into the radio task |
| Argument parsing | Every number goes through one helper with an explicit low and high bound before it is cast. Out of range, not a number, and missing are three different plain replies |
| Command validation | `radioWouldAccept` runs the same pure state machine the radio task runs, so a refusal is the radio's own answer rather than a second copy of the rules that could drift from it |
| Fail safe | A full queue answers 503 and a slow radio answers 202 with the state unchanged. Neither ever answers 200 for a command that was dropped |
| Secrets | `buildState` carries no PIN, no session token and no Wi-Fi credentials. The PIN is formatted in `handleRoot` into a local that is deliberately never sent |
| Auditing | Every accepted write prints one line to the serial log saying what it did, alongside the existing line for every wrong PIN and its source IP |
| Memory safety | The state document is built with `String` and three `snprintf` calls into local buffers of 72, 128 and 176 bytes, each given its own `sizeof`. No fixed buffer takes a caller supplied length |

## Raised by the code review, all fixed

The code review of this change found five defects. None was exploitable, and all five are fixed. They are recorded here because three of them are about a component reporting something untrue, which is the failure mode this project keeps finding.

### CR-01. A command the radio refused answered 200

`apiSubmit` judged a command with `radioWouldAccept` before sending it, against the last published state. For the five endpoints whose reply text is built from the request rather than from the result, a command the radio then refused still answered `200` with the text of what was asked for. Two clients, or one client after a 202, was enough: a `POST /api/step-size khz=9` that passed the check against a medium wave state was refused by the radio once a concurrent band change had moved it to FM, and the caller was told `200 step 9 kHz` while the step was 100.

Fixed by deleting the guess. The radio task now records what its own state machine made of each command, keyed by the ticket the caller holds, and `apiSubmit` reports that. There is one validation path, and it is the radio's. `radioWouldAccept` is gone.

### CR-02. The 202 path poisoned the next request

A command that was taken but not finished inside the wait left nothing to say it was outstanding, so the next request was validated against a state that predated it. Fixed by CR-01: there is no longer a check that runs ahead of the radio.

### CR-03. A failed publish stranded every later caller

The radio task applied commands and then published the count of them. If the publish could not take the lock, the count was lost for good, `applied` stayed permanently behind, and every later write answered 202 forever while the radio quietly kept working. It needs a broken mutex to happen and it cannot be recovered without a reboot. The task now carries an unpublished count forward to the next round.

### CR-04. Each write stalled the loop for most of a poll interval

See API-02 above.

### CR-05. The tune endpoint used its own copy of the band plan

`handleApiTune` worked out which band a frequency was in using `bandPlanDefaults`, while the radio task used the plan it was started with. They agree today because `main.cpp` passes the defaults. The moment the plan comes from settings, a medium wave spacing of 10 kHz or a different FM region moves the band edges, and the endpoint would name a band the radio was not on. The endpoint now asks the task for its plan.

## A note that is not a finding

The bug this change fixes has a security shape worth writing down. `radioWouldAccept` judged a command against the last published snapshot, which was up to 100 ms old. That was safe while a person turning a knob was the only source of commands, and the header said so. An HTTP API is a second source that can send commands faster than the radio publishes, and the check silently started answering about the state before the previous command. It refused things that were allowed, and reported frequencies the radio was not on.

Nothing was exploitable. The lesson is that a validity check against a cached copy of the state is only sound while the rate of change is bounded by something outside the attacker's control, and adding a network interface removes that bound. The check now runs against a state that has settled.

# Phase 2 addendum, the input layer

**Scope:** `core/input.c`, `drivers/encoder.cpp`, `drivers/keypad.cpp`, `drivers/i2c_bus.cpp`, `input_task.cpp`, the per band frequency memory and the cycle commands in `core/radio.c`, and the `input` field and `POST /api/cycle` in `net/web_update.cpp`. Same threat model: an attacker on the same LAN as the radio, or within Wi-Fi range of it.

**Status:** no new Critical, High or Medium finding. One accepted disclosure, and one availability note.

Physical input needs no PIN and never will. Whoever is holding the radio can already turn it off, so a gate on the knob would protect nothing and would lock the owner out of their own set. The PIN exists to stop someone on the network doing what only someone in the room should be able to do, and that boundary is unchanged.

## The gate

`POST /api/cycle` is a write and checks the session before it reads an argument, the same as the other eight. Verified on the radio: `403 Enter the access PIN first.` with no cookie. It carries no value from the caller at all, only which thing to move on, so there is nothing in it to range check beyond the four names it accepts.

## IN-01, accepted. The state document says what is being keyed at the radio

`GET /api/state` needs no session and now carries an `input` field: how many clicks and presses since boot, the last event in words, the digits keyed and not yet entered, and the raw state of the sixteen keypad lines.

So an unauthenticated caller on the LAN can watch, in near real time, that somebody is standing at the radio pressing buttons, and can read the frequency they are part way through typing.

**Accepted, not fixed.** What leaks is a frequency and the fact that a person is present. The same document already says what the radio is tuned to, which is the same information a moment later. Gating it would remove the one way to tell a dead switch from a wrong pin number on a radio that has no display yet, which is the whole reason the field exists.

**Residual risk:** somebody on the network learns that the radio is being used and what is being typed into it. Worth revisiting in phase 5 if the field survives past the display work.

## IN-02, note. One bus, two tasks

The tuner, the keypad and the clock share two pins. `drivers/i2c_bus.cpp` now serialises whole transactions, and the tuner holds the bus across a 2 ms settle after each write, five of those for a retune. A keypad read that arrives in the middle waits up to `I2C_BUS_WAIT_MS`, which is 100 ms, and then gives up rather than talking over the tuner.

This is not attacker reachable. No endpoint causes a keypad read, and the keypad is polled on a fixed 20 ms cadence whatever the network is doing. It is recorded because it is the first place where two tasks contend for one piece of hardware, and because the failure mode is silent by nature: see the finding below.

## IN-03, fixed. The bug worth writing down

Two tasks used the bus with no lock. That did not fail loudly. A tuner read is a write of the register wanted followed by a read of the answer, and a keypad transaction landing between the two returned zeros and reported success.

The result was a radio that read signal 0, bandwidth 0 and modulation 0 on shortwave, which is exactly what a dead band looks like. It was found only because an AM bandwidth of 0 is impossible: the filter is 4 kHz whether or not a station is there. Without that one impossible number it would have been put down to poor reception.

Three lessons, all of which have shown up before in this project:

1. A shared resource with no lock produces wrong data, not an error. Nothing in the logs said anything was wrong.
2. The failure imitated a legitimate condition. A quiet band and a broken read both read zero, which is the same shape as the stale snapshot problem in the control API, where a refused command and an accepted one both answered 200.
3. The tell was a value that could not physically occur. It is worth knowing, for every field published, which values are impossible.

## Checked and clean

| Area | Result |
|---|---|
| Injection | The `input` field is built from a fixed set of internal strings and from digits. Both go through `jsonEscape` anyway, so no value can break the document |
| Buffer safety | `sTyped` is nine bytes, capped at eight digits with the terminator at index eight. Every `snprintf` into the event text uses `sizeof` of its own buffer. The keypad line map is indexed 0 to 15 over a sixteen entry table |
| Command validation | The cycle commands take no value from the caller. The radio works out the next band, bandwidth or mode from its own state, which removed a class of bug rather than adding one |
| Fail safe | `i2cBusTake` refuses once the bus is started and no lock exists, rather than running unlocked. An unlocked bus returns plausible wrong data, which is worse than a read that fails |
| Physical input and the PIN | Input never posts a command a caller could not already send with the PIN. There is no privileged action reachable from the panel and not from the API |
| Secrets | Nothing in the input layer touches the PIN, the session or the Wi-Fi credentials |

# Phase 2 addendum, the display

**Scope:** `drivers/display.cpp`, `ui/screen.cpp`, `ui/font.h` and the two generated fonts, `screen_task.cpp`, and `tools/make_font.py`. Same threat model.

**Status:** no finding at any severity. The display is an output with no input, which is why this section is short, and the reasoning for that is worth stating rather than leaving as an assumption.

## Why there is almost no attack surface here

Nothing reaches the panel from the network. `screen_task.cpp` reads a snapshot of the radio's state and turns it into strings; every one of those is either a number the radio measured or a pointer to a string literal chosen by a switch. No text a caller supplies, over HTTP or otherwise, is ever drawn. The nearest thing is the Wi-Fi network name, and that goes to the web page, not to the panel.

Nothing is read back from the panel either. SPI is write only here, MISO is not attached, and no code path turns pixels back into data. So there is no parser and nothing to confuse.

| Area | Result |
|---|---|
| Buffer safety, glyphs | `sGlyph` is 64 by 40. `displayText` refuses a font taller than 40 and clamps the width to 64, so the largest index written is `height * w - 1`, inside the array. The two fonts are 12 and 22 pixels wide and 18 and 31 tall, so neither limit is reached |
| Buffer safety, font data | Checked the arrays against their own tables. The small font is 2124 bytes and its last glyph ends at exactly 2124; the large font is 1054 and ends at 1054. No read past either |
| Generated code | The generator now refuses to emit a font whose glyph offsets would not fit the `uint16_t` they are stored in, rather than wrapping silently, and exits non zero when it fails |
| Rectangles | `displayFill` clips to the panel through a signed intermediate, so a negative position cannot wrap into a huge unsigned window. `displayPush` refuses an off panel rectangle outright rather than drawing part of it |
| Strings | Every `snprintf` uses `sizeof` of its own buffer. The remembered lines are 64 bytes, longer than the longest string any field can hold, which was not true at first and made one field redraw itself for ever |
| Concurrency | `radioGetSnapshot` copies under the lock and releases it before anything is drawn. No lock is held across SPI. The panel is only ever touched from the loop task |
| Availability | A full screen clear is the most expensive thing here, and the loop task does not run while it happens. It is now a burst write rather than a byte at a time, and the redundant clears at start up were removed. Not reachable from the network in any case |

## A note that is not a finding

The SPI bus transaction was held open for the life of the firmware. That is not a security problem today, because nothing else uses the bus, but it is a deadlock waiting for phase 4: the touch controller shares the bus, needs a slower clock, and would have blocked for ever on the semaphore with no timeout. It now takes and gives the bus per operation.

Worth recording next to the I2C finding above, because it is the same shape. Both are a shared piece of hardware with no arbitration, and in both cases the failure is silence rather than an error.

# Phase 2 addendum, the reception defaults

**Scope:** `applyReceptionDefaults` in `drivers/tef668x.cpp`, nineteen configuration writes to the tuner at start up. Same threat model.

**Status:** no finding. Recorded because "no finding" is worth writing down with the reason, not left as an assumption.

There is no input here. Every value is a compile time constant, the sequence runs once during start up before the network is up, and nothing about it can be influenced by a request, a person at the radio, or anything on the air. No buffer takes a caller supplied length: the argument array is sized to what the command helper accepts rather than to what this function passes, so a longer command added later cannot read past its end.

| Area | Result |
|---|---|
| Input | None. Nineteen writes of fixed values, no parameter from anywhere |
| Reachability | Start up only, before Wi-Fi, before the web server |
| Memory safety | `args` is sized to the helper's maximum, not to current use |
| Availability | A failure is reported and start up continues. These are quality writes, and refusing to start would turn a radio that sounds wrong into a radio that does not work, which is worse and which the owner cannot fix from where they are standing |

The values were all correct. Two of the comments describing them were not: they said the stereo blend and the treble roll off were being switched on, when mode 0 in both cases switches them off. The reference firmware ships with both off, so the code was right and the explanation was inverted.

That is a documentation defect rather than a security one, and it is in this file because of what it would have cost. Someone reading "a weak station goes to mono rather than hissing in stereo" and hearing hiss would go looking for a fault in the blend, which was never on. # Phase 2 addendum, the volume knob

**Scope:** `drivers/analog.cpp`, the pot curve in `core/input.c`, the pot polling in `input_task.cpp`, the meter call in `screen_task.cpp`, and the change to `pushToTuner` in `radio_task.cpp`. Same threat model.

**Status:** no finding. One disclosure recorded, and one availability note that is really a correctness note.

## The knob is physical, and that is the whole point

The pot is an ADC pin. Nothing on the network can move it, and nothing it produces is parsed: it is a number from 0 to 4095 that goes through a clamped mapping into a volume in dB, bounded on both sides by the range the tuner accepts. There is no string, no length and no allocation anywhere in the path.

The meter is write only. Nothing is read back from it, and no meter is fitted on this unit in any case.

| Area | Result |
|---|---|
| Input | One ADC reading. Every value it can take is inside the mapping's clamps, checked by test across the whole range |
| Arithmetic | Widened to 32 bits before the multiplication, clamped both ends, and guarded against a configuration whose ends are equal |
| Allocation | None |
| Concurrency | ADC1, which is the half that keeps working with Wi-Fi on. No lock, nothing that blocks. Eight conversions every 50 ms on the loop task |
| Precedence | The knob overrides a volume set over HTTP the next time it moves. That is what a physical control has to do, and it means the knob is the last word on how loud the radio is |

## POT-01, accepted. The state document says where the knob is

`GET /api/state` needs no session and now carries the pot reading and the volume it maps to. An unauthenticated caller on the LAN can see the volume being changed, and therefore that somebody is at the radio.

**Accepted.** The same document already says what the radio is tuned to and what the last button press was, which is the same class of thing and was accepted as IN-01. It is a volume setting.

## A note that is not a finding

Every volume change used to mute the tuner, retune it and unmute it. With a knob sending a change every fiftieth of a second that is audible as the sound breaking up, which is how it was found.

The security shape is worth recording: the fix was to do only what changed, and the first attempt at it returned early when the initial mute failed, leaving the tuner muted with nothing on any later path to unmute it. That is the same permanent silence this project has already hit once on the AM side. The comment above that code claimed every path reaches the unmute, and it was the one path that did not.

A comment asserting a safety property is not the property. This is the second time in this audit that a correct-looking comment sat next to code that did not do what it said.

# Phase 2 addendum, the squelch

**Scope:** `core/squelch.c`, the squelch state and the mute handling in `radio_task.cpp`, the knob's change of job in `input_task.cpp`, and `POST /api/squelch` with the `sql` fields in `net/web_update.cpp`. Same threat model.

**Status:** no new Critical, High or Medium. One finding fixed before it shipped, and it is the important part of this section.

## SQ-01, fixed before shipping. A tuner that stopped answering would have silenced the radio for good

The squelch shuts the audio when a reading says there is nothing worth hearing. The first version treated a reading that failed to arrive as "say nothing, change nothing", which sounds careful and is not.

The sequence: the squelch shuts on noise. The tuner then stops answering on I2C, for any reason. Every later reading is a failure, the failure branch changes nothing, and the audio stays shut. There is no squelch control on the front of this radio, so the only ways out are an HTTP request or a power cycle.

That is the third time in this project that a fault in one component has been paid for by the listener, and the second time it would have ended in permanent silence. The others are recorded above as the AM bandwidth trap and the mute that returned before its unmute.

Now a failed reading holds the current state, so one failure in the middle of a bad patch cannot postpone the shut, and readings that keep failing for as long as the hold open the audio again. The reasoning is that silence needs evidence, and a tuner that is not answering is not evidence.

| Area | Result |
|---|---|
| A deliberate mute | Kept apart from the squelch everywhere, and combined only where the tuner is told. The squelch can never unmute something the person muted, and turning the squelch off can never leave a muted radio playing |
| Start up | The squelch is initialised open, not zeroed. A zeroed one is shut, and the radio would have come up silent before its first reading |
| The hold | Started again when the band or the mode changes, so a wait begun under one rule is never counted towards a decision made under another |
| Input validation | `mode` is checked against the three names. `threshold` is refused outright, see below |
| Arithmetic | The pot to threshold mapping is clamped at both ends and monotonic across the whole converter range, checked by test |
| JSON | `sql`, `sqlOpen` and `sqlAt` quote and comma boundaries checked character by character, the failure this file already records once |

## SQ-02, fixed. The API took a value it could not honour

`POST /api/squelch` accepted a `threshold` and answered with it. In manual mode the knob is the threshold, so the knob replaced that value within a fraction of a second, and the reply was untrue before the caller could read it. Measured: a request setting 10.0 dBuV read back as 53.2 dBuV four tenths of a second later.

Two owners for one value. The argument is refused now, with a reason that says where the value comes from instead.

This is not a security finding by itself. It is here because it is the same failure as the control API answering 200 for a command the radio refused, and the same as the two inverted comments: a component saying something that is not so, where nothing downstream can tell.

## A note on ordering

The endpoint used to write the threshold before it had validated the mode, so a request that answered `400` had already changed the radio. Everything is checked before anything is written now. Worth stating as a rule rather than a fix: an endpoint validates completely, then acts.

# Phase 2 addendum, the FM features

**Scope:** `core/signal.c`, the four new tuner writes in `drivers/tef668x.cpp`, the feature settings in `core/radio.c`, the bandwidth extension and `pushFeatures` in `radio_task.cpp`, and `POST /api/fm` with the new state fields in `net/web_update.cpp`. Same threat model.

**Status:** no finding at any severity. Three defects fixed before shipping, all of the same family, and one diagnostic added because the radio produced a fault this document could not explain.

## What is here and why it is short

`POST /api/fm` takes three arguments, each 0 or 1, behind the PIN like every other write. There is nothing to overflow: no string, no length, no allocation. The bandwidth extension takes nothing from anybody, it follows the signal.

| Area | Result |
|---|---|
| Input | Three arguments, each bounded to 0 or 1 by the shared helper. Every argument is validated before any command is sent |
| Arithmetic | The signal to noise line is integer, in 64 bits where the terms need it, checked against the floating point original over six million combinations per band |
| Refusals | An FM feature asked for on an AM band is refused with its own reason rather than the message for a band that does not exist |
| Partial application | Three features are three commands. A failure partway now names which one failed and what the radio actually reached, instead of a bare no |
| JSON | Five new fields, quote and comma boundaries checked. `snr` is an `int8_t` and is printed as a number, not as a character |

## FM-01, fixed. A rounded constant moved a threshold

The signal to noise figure is computed, not read. The first version scaled the reference's constants by a million to keep the arithmetic in 32 bits, which rounded 0.0082495118 to 0.00825.

That disagreed with the original in 6874 of six million combinations, by a whole dB, and **six of those straddled the test that opens the filter**. At 30.4 dBuV with 97.6 per cent noise the reference opens the filter and this firmware would not have.

The comment claimed the disagreements were all below -16 dBuV and therefore harmless. That was wrong, and it was wrong in the confident direction: it gave a reason not to look. It is now 64 bit arithmetic with the full constants, and disagrees once in six million, at 49.4 dBuV with 337 per cent noise, nowhere near anything that reads it.

CLAUDE.md's rule is no guessed thresholds, because a guessed one switches a feature off silently. This is the same failure arrived at from the other end: the threshold was right and the arithmetic feeding it was not.

## FM-02, fixed. An FM formula was being applied to AM readings

The AM side reports its noise on a scale fifty times larger, and the reference divides that field before putting it through the same line. This did not, so every AM reading produced a signal to noise figure far below the truth, which went out in the state document and into the smoothing the bandwidth extension reads.

## FM-03, fixed. The smoothing carried readings across a band change

The averages behind the bandwidth decision were fed on every poll, whatever band the radio was on and whether or not the reading had arrived. A failed read pushed the previous sample in again as though it were new, and time on medium wave filled the averages with AM numbers. Coming back to a strong FM station, the filter stayed narrow for about two seconds while the smoothing forgot.

They are now fed only by readings that arrived from the FM side, and started again on a retune, because a reading from somewhere else on the dial says nothing about where the radio is now.

## A diagnostic, added because of a fault this document could not explain

During this work the radio was found silent, and a power cycle fixed it. The state document could not say why: it reports the mute the person asked for, and the tuner is told that or silence from the squelch, and there was no way to see which.

`hwMute` is what the tuner was last told. A radio that is quiet with `mute` false and `hwMute` true has been silenced by something other than the person, and that is now visible without a serial cable.

The cause of that particular silence is not established. The radio had also restarted on its own shortly before, which is its own open question. Recording both rather than leaving it as a story about a power cycle.

# Phase 2 addendum, the weak signal controls and the fades

**Scope:** the weak signal and noise blanker controls in `drivers/tef668x.cpp`, the processing status read, the volume fade in `core/radio.c` and `radio_task.cpp`, the start up ordering in `main.cpp`, and the eight argument `POST /api/fm`. Same threat model.

**Status:** no finding at any severity. Recorded for the two near misses, both of which are about a control that appears to work and does not.

| Area | Result |
|---|---|
| Input | Eight arguments, each range checked before any command is sent. The ranges are now the chip's, not a guess |
| Where the rule lives | The noise blanker range is checked in `core/radio.c`, not only in the web handler, so a future menu cannot set a value the API refuses |
| Group edits | An omitted member of a group keeps its value, seeded from the radio. When the radio cannot be read the request is refused rather than sending zeros, which would switch off what the caller did not mention |
| Partial application | A refusal names which argument failed and what the radio actually reached. The half that works on AM is applied before the half that does not, so an FM only refusal no longer takes the blanker down with it |
| Availability | The fade shortens the radio task's wait while it runs. It only shortens a wait that was already longer, so commands are picked up sooner, never later, and the poll cadence is independent |
| Permanent silence | Traced again. The fade always converges on the target, `settings` always holds it, and any gap between what was pushed and what is wanted forces a write |

## WS-01, fixed. A control that was switched on and could do nothing

The stereo high blend takes four commands: three that say when to act and one that sets its ceiling. Only the first three were sent. The mechanism was on, reported as on, and applied nothing, because its limit had never been set.

It was found only because the processing status read was added first and showed two numbers moving and the third stuck at zero. Without that read it would have looked like a working feature.

The same shape appears twice more in this change and was caught by the same reasoning: a noise blanker range that accepted values below the chip's usable floor, and weak signal start levels that accepted a level no signal reaches. Both would have been settings that could be turned on and do nothing. Both are refused now, with a reason that says what the range is.

## WS-02, fixed. The fade ran backwards

The volume fade after a band change started **after** the push that carried the retune, so the tuner unmuted at full volume, dropped twenty five dB on the next pass, and ramped back. Twenty milliseconds of full volume, then a step down, then the fade.

It survived a listening test. The listener reported it as smoother, because it still ended in a ramp and the burst is short. It was found by reading the order of the two statements.

Not a security defect. It is here because it is the clearest example in this project of something that cannot be judged by using it: the feature appeared to work, the person using it said it worked, and it was doing close to the opposite of its purpose.

## A note on what these checks are worth

Three of the defects in this change were ranges that accepted a value which switched something on to do nothing. None of them would have failed a test, produced an error, or looked wrong on the page. DECISIONS.md already says a guessed threshold silently switches a feature off rather than failing, which is why it is banned. The same applies to a range: a range that is wider than the hardware's is a guess wearing a check's clothing.

# Phase 3 addendum: the stored settings

Scope: the uncommitted change on `dev` that takes the settings struct to version 2 and wires it through. `GET` and `POST /api/settings` with their new fields, the new `POST /api/save`, the `deemph` argument on `POST /api/fm`, the changed `radioTaskStart`, and the new Radio section on the root page with its inline script. Judged against an attacker on the same LAN or in Wi-Fi range.

Score: **GREEN.** No critical and no high. One low, recorded below, and it needs the PIN first.

## SET-01, clean. The larger settings report says nothing secret

`GET /api/settings` went from three fields to nineteen. Every one of the new fields is a number a person chose: a band plan, a start level, a blanker percentage, a de-emphasis time constant. The two secret fields in the struct are reported the way they always were, as `hasPass` and `defaultPin`, which say whether each one is set and never what it is. The Wi-Fi passphrase and the access PIN are never put into the body.

The one string in the reply, the stored SSID, still goes through `jsonEscape`. The other new string, the squelch mode name, comes from `squelchModeName` and is one of three literals in this firmware.

The whole endpoint is behind `requireAuth(false)` in both directions, so none of it is readable without the PIN in the first place.

## SET-02, clean. The PIN gate is on both new paths

`handleApiSave` calls `requireAuth(false)` as its first statement, before it reads the radio or touches NVS. `handleApiSettingsPost` does the same, before it parses any of the four new arguments. A caller with no session gets 403 and nothing is read and nothing is written.

## SET-03, clean. A blob the radio would refuse cannot be written

The question was whether a request could store a settings blob that the next start refuses, leaving the radio on the defaults with no explanation. It cannot, and there are two layers:

1. Both write paths call `settingsValid` on the whole pending struct before saving, not only on the fields the request touched, and answer 400 rather than storing it.
2. `settingsNvsSave` calls `settingsValid` again and refuses to write at all.

The ranges those checks use are now the enums themselves, `FM_REGION_COUNT`, `MW_SPACING_10K`, `ENCODER_OPTICAL`, `SQUELCH_MODE_COUNT`, `BAND_COUNT`, rather than numbers written by hand in `settings.c`. The hand written numbers were correct, but they were a second copy of the enum that would have gone wrong silently the day a member was added.

The migration path was checked separately: a version 1 blob is 108 bytes, that length is now pinned by a test that asserts the offset of every version 1 field, and a blob of any other length for that version is refused as corrupt rather than read short.

## SET-04, note, not a finding. A stored frequency the band plan no longer holds

Storing a station on 102.8 MHz and then setting the FM region to Japan leaves a stored frequency the band cannot reach. `radioFromSettings` hands it to `radioApply`, which moves to whichever band holds it, and when no band does it is refused and the stored band's own starting point is what is left. The radio comes up on a real frequency either way. There is no path here to a radio that comes up silent or on nothing.

This is availability of the radio to its owner rather than security, and it is recorded because "comes up wrong after a settings change" is the shape of fault this project keeps finding.

## SET-05, low. Nothing rate limits a write to flash

**A signed in attacker on the LAN can loop `POST /api/save` or `POST /api/settings` and write NVS as fast as the radio will answer.** NVS is wear levelled, and the IDF layer skips the write when the value is unchanged, so a loop that posts the same thing costs nothing. A loop that alternates two valid values, say `region=0` and `region=1`, does write every time.

Severity is low and not medium for three reasons: it needs the access PIN, the attacker has to be on the LAN, and anyone who has both can already replace the firmware, which is a larger power than wearing out a partition.

Not fixed here. Recorded so the decision is deliberate. If it is ever worth fixing, the fix is a minimum gap between writes in the handler, not a token.

## SET-06, clean. The new page section is not an XSS route

The Radio section is built by `radioForms`. Everything it emits is either a string literal in the firmware or a number out of the validated settings struct, put through `String(long)`. No caller supplied string reaches it. The two user supplied strings on that page, the network name and the stored SSID, are in the older Wi-Fi form and still go through `escapeHtml`.

The inline script has no interpolation: it is a fixed string in `pageTail`, it finds its forms with `querySelectorAll`, and it puts the reply into the page with `textContent`, not `innerHTML`. A hostile reply body from a man in the middle would be displayed as text, not run.

Worth saying plainly: the forms post to the same API endpoints a script uses, rather than to handlers of their own. That is a security property as well as a design one. There is one place that checks each range and one place that words each refusal, so there is no second path with a weaker check on it.

## SET-07, clean. No new way to block the radio task

`POST /api/save` reads the radio through `radioGetSnapshot`, which takes the mutex with a 50 ms timeout and answers 503 when it cannot. It posts no command and waits for no reply. The `deemph` argument on `/api/fm` goes through `radioPostAndSettle` with the same `API_SETTLE_MS` bound every other argument on that endpoint uses. Neither adds an unbounded wait, and neither holds the lock across a tuner write.

## CSRF, unchanged

The new writes are simple form posts with a session cookie, exactly like the ones SEC-07 already covers. The defence is unchanged: the cookie is `HttpOnly; SameSite=Strict`, so a cross site post carries no cookie and `requireAuth` answers 403. SEC-07 stays open as defence in depth and this change does not widen it.

## Found by the code review, after this addendum was first written

Four defects were found reviewing the same change, and two of them are worth recording here because they are the shape this document keeps tracking: a control that is accepted and then does the opposite of what it says.

**A bandwidth from the wrong band's list silenced FM.** `RADIO_SET_BANDWIDTH` accepted anything from 0 to 6000 kHz. The two lists do not overlap, 3 to 8 kHz on AM and 56 to 311 on FM, so an AM width on FM pinned the filter far narrower than a station. The chip then reports its narrowest bandwidth, finds no stereo pilot and no signal, and the radio reads as one with no aerial. The new web form made it a single button press. The range now comes from the band's own list, through `bandBandwidthAllowed`, and the form is not offered on FM at all.

This is the same defect as the three in the phase 2 addendum, and it was in code written before that addendum. A range of 0 to 6000 was never a check: nothing in the radio accepts 6000, and nothing accepts 110 either.

**A stored squelch mode changed what the knob means, and the volume was read off it anyway.** In manual squelch the knob is the squelch control and never sets the volume. Restoring that mode at start up meant reading a volume off a knob that was set to a threshold: full volume at one end of the travel and silence at the other, with nothing to correct it, because the knob never touches the volume in that mode. The fix is `startVolumeDb`, stored and read only in that mode.

Not security defects. Both are here because the common cause is one this document has now recorded five times: a value that is accepted, reported as set, and does something other than what its name says.

## SET-08, accepted. The number boxes accept what the API refuses

The three weak signal levels take 0, or 20 to 60. The blankers take 0, or 50 to 150. HTML cannot express either range in one number box, so the page offers the whole span and the API answers 400 for the gap. The hint text says the real range and the reply says it again in red.

A select of fixed values would stop it in the browser, at the cost of every value in between, and of showing the wrong current value whenever something was set through the API to a value not in the list. The number box keeps every valid value reachable and never misreports what the radio holds. Recorded as a deliberate choice rather than an oversight.

## A setting that may be doing nothing, recorded rather than assumed

The FM de-emphasis added in this change was tested by ear on 13 September 2026, on FM 106.4 MHz, a station reading 37 dBuV with an ultrasonic noise of 9. Two blind A/B tests, order picked at random and not looked at until after the answer: 75 us against 50 us, then off against 50 us. Both came back as no audible difference.

The second pair is the one that matters. Switching de-emphasis off removes the treble correction altogether, which is not a subtle change, so a null result there is evidence the command is not reaching the chip or not being acted on.

What is known: the write returns `TEF668X_OK`, `GET /api/state` reports the value back, the module and command numbers are FM 32 and 31, and the argument is tenths of a microsecond, 500 and 750, all matching the reference firmware that runs on this board. So whatever is wrong is not visible from the API.

It is written down here rather than left as a working feature because a setting that is accepted, reported as set, and does nothing is the failure this document has now recorded six times. It is not a security defect. It is open.

# Phase 3 addendum: the web pages, seek and the pot calibration

Scope: everything on `dev` since 882b711. The four web pages and their inline script, `POST /api/seek`, `POST /api/pot`, the fields added to the state document, and the settings migration now that it is at version 4 and copies by field end rather than by stored length. Judged against an attacker on the same LAN or in Wi-Fi range.

Score: **GREEN.** No critical and no high. Two defects were found and fixed during the audit, both in the pot calibration, and neither is a security defect.

## WEB-01, clean. Nothing new is reachable without the PIN

Checked on the running radio rather than only in the code. Every write endpoint, with no session cookie:

```
api/seek      403    api/settings  403    api/bandwidth 403
api/pot       403    api/fm        403    api/tune      403
api/save      403
```

All four pages answer 200 signed out, and none of them renders a control that changes anything: the count of `data-post` elements and of the firmware and PIN forms is zero on every one. A signed out visitor sees the status and a PIN box.

## WEB-02, clean. The sign in redirect is not an open redirect

`safeNext` compares the submitted `next` against the four paths this firmware serves and returns the home page for anything else. Tested against the shapes that usually get through:

| Sent | Landed on |
|---|---|
| `http://example.com` | `/` |
| `//example.com` | `/` |
| `javascript:alert(1)` | `/` |
| `/../etc` | `/` |
| `/radio?x=1` | `/` |
| `/radio`, `/system` | themselves |

The protocol relative form is the one worth calling out, because a check that only looks for a scheme lets it through and the browser treats it as another origin. This one compares whole strings against a list, so there is nothing to slip past.

The value is also never attacker controlled on the way in: `signInForm` is called with a literal by each page handler, so the hidden field holds one of four fixed strings.

## WEB-03, clean. The page and its script are not an XSS route

The Radio page is built from string literals and from numbers out of the validated settings and snapshot, all through `String(long)`. The only user supplied strings anywhere in the four pages are the network name and the stored SSID, both of which still go through `escapeHtml`.

The inline script has no interpolation. It is a fixed string in `pageTail`, finds its controls with `querySelectorAll`, and writes every reply into the page with `textContent`. A hostile reply body would be displayed as text, not run. It is also served only on the Radio page now, so the other three carry no script at all.

## SEEK-01, clean. A seek cannot be used to wedge or silence the radio

`POST /api/seek` posts one command and returns. It does not wait. The seek itself is a state machine in the radio task that walks one channel per round, and it ends in one of two ways: it stops on a station, or it gives up after one full pass of the band. Both call `seekEnd`, which unmutes. There is no path that leaves the radio muted, and the loop is bounded by the channel count of the band, which is 206 on FM and 17 on long wave.

Any other command cancels it, which is what the drain loop does before applying anything that is not a seek. So an attacker cannot hold the radio in a seek: the owner turning the knob ends it.

## POT-02, fixed. Cancelling a calibration did not cancel it

**Found by this audit, not by testing.** `inputPotCalibrateCancel` cleared the running flag but left the extremes it had recorded. A `finish` afterwards read those stale values and applied and stored them, so pressing Cancel and then Done stored the sweep that had just been cancelled.

Not a security defect: it needs the PIN, and the worst case is a knob mapping the owner did not want. It is recorded because it is a control that says it does one thing and does another.

Fixed by making `potCalibrateFinish` refuse when no calibration is running.

## POT-03, fixed. A calibration left open disabled the volume knob for good

**Also found by this audit.** While a calibration runs the knob sets neither the volume nor the squelch, by design, so that sweeping to the loud end stop is not painful. Nothing ended it except a `finish` or a `cancel`.

So an authenticated caller could `POST /api/pot -d 'action=start'` and walk away, and the radio would have no working volume control until somebody power cycled it, with nothing on the radio to say why. As a denial of service it is weak, because it needs the PIN and anyone with the PIN can already replace the firmware. As a fault it is worse than that, because the owner has no way to work out what happened.

Fixed with a two minute timeout inside `potCalibrateSample`, which is far longer than turning a knob to both ends takes. When it fires the knob takes its job back on the same poll.

## POT-04, note. Both defects existed because the code was in the wrong layer

The calibration state machine was first written in `src/input_task.cpp`, which uses the Arduino API and therefore cannot be tested on a PC. Neither defect could have been caught by a test while it lived there.

It now lives in `core/input.c` as `potCalibrate*`, with seven tests including the cancel case, the timeout, the millisecond wraparound and the refusal of a sweep that barely moved. The layering rule in CLAUDE.md, that `core/` has no hardware dependencies, is not only about portability: code that cannot be tested does not get tested.

## SET-09, clean. The migration cannot read a field out of another version's padding

Version 4 added `potRawMin` at offset 134, which is inside the two bytes version 3 wrote as padding after its last field. Copying a version 3 blob by its stored length of 136 would take the new field out of that old padding.

It is zero on every radio in the field, because the struct is memset before it is filled, so this could not have been exploited. It is fixed anyway, because "it happens to be zero" is not a reason. `settingsFieldEndOfVersion` gives the offset where each version's fields end, expressed with `offsetof` so it cannot drift from the struct, and the copy stops there. A test writes 0xAB and 0xCD into that padding and checks the calibration reads back as not set.

The rest of the migration is unchanged and still refuses a blob whose declared size does not match both its actual length and the size that version wrote, which is what stops a truncated blob being read as a valid short one.

## Rate limiting, unchanged

`POST /api/pot` with `action=finish` writes NVS, the same as `/api/save` and `/api/settings`. SEC-05 already covers this: nothing rate limits a write to flash, it needs the PIN, and anyone with the PIN can replace the firmware. No change.

# Phase 2 addendum: the FM feature cycle

POST /api/cycle wht=fm   ->   403 Enter the access PIN first.

# Phase 4 addendum: the audio polish

Scope: ticket 19's audio group. The volume ramp on mute, on the squelch and across a bandwidth change; the tuner's tone generator and the beeps that use it; `radioHush` before a reboot or an update; settings version 5; and `POST /api/beep`.

Score: **GREEN.** Nothing found.

## BEEP-01, clean. The audio source cannot be left pointing at the generator

The one thing in this change that could make the radio silent with no explanation. The tone generator is not heard unless the audio input selector is switched to it, command 12 with 240, and the radio hears nothing but the generator while it is. So a tone that starts and never stops would leave a radio that is on, tuned, unmuted, reporting a good signal, and completely silent.

Three things stop it, and the first is the one that matters:

1. **The selector is put back whatever the tone write did, and it is tried again until it works.** In `tef668xTone` the return to the tuner is attempted on the way out even when turning the generator off failed. That alone was not enough: the caller in the radio task discarded the result and cleared its state anyway, so one failed I2C write would have left the selector on the generator with nothing ever retrying. The task now keeps the tone marked as sounding until the off call returns `TEF668X_OK`, so it comes round again the next time through the loop.

   This was scored clean here before that retry existed, on the strength of what the driver does rather than what the caller does with it. The review caught it. A radio pointing at a silent generator is a radio that has gone dead, so it is worth saying what the mistake was: the claim was true of one function and false of the pair.
2. **The order is deliberate.** Going on, the source is selected before the tone starts. Coming off, the source returns before the generator stops, so the station is back before the tone ends rather than leaving a gap of nothing between the two.
3. **The stop is not conditional on anything.** The task ends the tone on a clock, in the same loop that ends a seek, and nothing about the audio state can hold it open.

Checked on the running radio: after a beep, `bep` is false and the signal and stereo flag read normally, which they could not if the path were still on the generator.

## BEEP-02, clean. The endpoint is behind the PIN and bounded

```
POST /api/beep  ms=1000   no session   ->  403
POST /api/beep  ms=99999               ->  400  ms has to be between 1 and 3000
POST /api/beep  ms=0                   ->  400
```

Three seconds is the ceiling, so an authenticated caller can annoy somebody standing at the radio but cannot hold the audio path for longer than that, and a following request does not extend it: the task keeps one deadline, not a queue of them.

## MUTE-01, clean. The ramp cannot leave the radio muted

The soft mute holds the mute back while the volume walks down, so for the length of the ramp the radio is unmuted and quiet rather than muted. The state that decides is recomputed from `wanted.muted`, the squelch and the seek on every round, so nothing latches: if the reason for muting goes away mid ramp, the ramp is abandoned and the volume returns on the next push.

The failure that would matter is the opposite one, a radio left silent, and the existing push machinery covers it. `pushFailed` re-sends everything after any failure, and the mute and the volume both go out on that path.

## MUTE-02, clean. The bandwidth mute restores what it found

The brief mute around a filter change only happens when the radio is not already muted, and the unmute is attempted whatever the bandwidth write did. Muting something already muted and unmuting it afterwards would turn the audio on for somebody who asked for quiet, which is why the condition is there rather than an unconditional pair.

## Not a finding. `radioHush` reaches past the radio task

`radioHush` writes to the tuner from the web task, which every other path avoids: the tuner belongs to the radio task and commands reach it through a queue. It is safe only because of what follows it, a reboot, and it is the one caller that can say that. It is called from `webLoop` immediately before `ESP.restart()`.

If that ever moves, or something is added after it, this becomes a genuine two writer problem on the I2C bus. Written down here rather than left to be discovered.

## What the review of this change found

Ten findings, two of them serious, and both were in the part of this change that touches the audio path rather than in anything with a network on it.

**A failed tone off would have silenced the radio for good.** Recorded above under BEEP-01, which had been scored clean on the driver's behaviour without checking what the caller did with the result.

**The ramp made the click louder rather than removing it.** On the round the ramp finished, the volume was recomputed from the fade, which is the full target, and `pushToTuner` writes the volume before the mute. So after walking down to silence over 120 ms the radio jumped back to full volume for the length of one I2C transaction and then muted. That is a worse click than the one the ramp exists to remove, and nothing would have caught it except listening for the exact thing the feature claims to fix.

Neither is a security defect. They are here because both are the same shape as the failures this document keeps recording: a feature that reports success while doing the opposite of what it says.

Two more worth noting for the record:

- `radioHush` reaches past the radio task to the tuner, and the task kept pushing for the two hundred milliseconds before the restart. It now sets a flag the task checks, so once the hush has run nothing else writes to the tuner. Before that, a turn of the knob in that window would have put the volume straight back and put two tasks on the I2C bus at once.
- The beep's pitch was passed in a global that the calling task wrote and the radio task read later. Two beeps asked for at once would both have played at whichever pitch was written last. It travels on the command now, which is what the file's own header says about everything crossing that boundary.

## A rename that left four tables behind

Not a security defect, recorded because of how it failed rather than what it was.

The state document keys and the request arguments were shortened to three letters. The rename was applied to `sServer.arg("x")`, `hasArg("x")` and `apiNumber("x"`, which is every place an argument is *read*. It was not applied to the four tables inside the handlers that hold argument names as data:

| Table | Held | Should have held |
|---|---|---|
| `stored[]` in the settings handler | `region`, `spacing`, `encoder`, `direction`, `fmsens`, `amsens` | `rgn`, `spc`, `enc`, `edr`, `fsn`, `asn` |
| `features[]` in the FM handler | `mono` | `mno` |
| `names[3]`, the weak signal levels | `blend`, `hiblend` | `bld`, `hbl` |
| `names[2]`, the blankers | `amnb`, `fmnb` | `anb`, `fnb` |

So the web page posted the new name and the handler looked for the old one. Every band plan control and the seek sensitivity had been doing nothing since the rename.

**Two of them failed silently.** The weak signal levels and the blankers are guarded by an outer `hasArg` on the new name, which passed, and then looked up the value with the old name, which did not match. The endpoint answered 200 and reported the setting unchanged. Reproduced before fixing: `POST /api/fm -d 'bld=30'` replied `weak signal cut 45 blend 0 hiblend 0`.

It was found by listing the field names the page actually serves and posting each one, rather than by testing the API with names taken from the code. The names in README.md were right the whole time; the code was wrong. Checks 290 to 294 are that comparison written down.

A separate instance of the same shape, found by the review in the same pass: `fields[]` in the settings handler had nine entries for ten rows of `stored[]`. The tenth was value initialised to NULL, the apply loop skips NULL, and the chime's switch saved nothing while replying "Saved". The array is sized from the table, so a short initialiser list is not a compiler error. There is now a run time check that counts the entries against the rows and refuses the request rather than quietly ignoring a field.

## A failed update leaves the radio silent for good

Availability, found on the radio on 13 September 2026 while running check 282a.

An update over the air hushes the radio the moment the transfer starts. `ArduinoOTA`'s `onStart` calls `radioHush`, which walks the volume down, mutes the tuner, and sets a flag that stops the radio task writing to the tuner at all. That flag is right for its purpose: the caller is about to restart, and anything still writing would put two tasks on the I2C bus during the shutdown.

Nothing cleared it. `onError` recorded the reason and returned, and the flag is only ever false at boot. So a transfer that broke halfway left the radio with no way back: the knob, the keypad and every API call were all shut out of the audio, and only a power cycle brought it back.

It was not visible from outside. The radio kept serving, kept its Wi-Fi, and reported a station, a good signal, `mut` false and `hmu` false. Both of those are what the radio task last decided, and the task had stopped deciding. Every reading a person would check said the radio was playing.

The reproduction was accidental and exact: the first espota attempt across two subnets got to 11 per cent and broke, and the radio went quiet while still answering every request normally.

Fixed with `radioResume`, called from `onError`. It clears the flag only. The task already holds what it last pushed against what the settings ask for, and `radioHush` left those disagreeing, so the next round finds the difference, sends it, and fades the audio back up because the last pushed state was muted. Check 282c covers it, and says to judge by ear because the state document reads the same either way.

The same shape as the rest of this file: a component reporting something untrue, where the untruth is indistinguishable from a legitimate condition. Here the untruth was "the audio is on", and the thing that made it untrue was the one piece of state deliberately placed outside the reporting path.

`sHushed` is now `volatile`. It is written by whichever task is shutting the radio down and read by the radio task every round, and it was neither before.

## Phase 3 addendum: the bandwidth ramp and radioResume

Audited on 13 September 2026, against `edf695b` plus the working tree. Threat model is an attacker on the same LAN or in Wi-Fi range, not the internet. Scope: `radioResume` and its call from the OTA error path, `sHushed` becoming `volatile`, the bandwidth ramp in the radio task, and the five corrected refusal messages.

Result: **GREEN.** No critical and no high findings. One medium, one low, and two recorded decisions. All three findings are fixed; the decisions are accepted with their residual risk written down.

### Low: the OTA error path resumes the audio even when it never hushed it

`ArduinoOTA` fires `onError` with `OTA_AUTH_ERROR` when an invitation arrives with the wrong password. That happens before `onStart`, so no hush has run, and the new `radioResume` call clears `sHushed` anyway. Anyone who can reach UDP port 3232 can trigger it without knowing the PIN, which was confirmed on the radio: an invitation sent with the password `999999` was refused, and the error callback ran.

It is not exploitable today. The only other caller of `radioHush` is `webLoop`, which hushes, blocks for two hundred milliseconds, and restarts, all in one call with no `ArduinoOTA.handle()` in between, so the error callback cannot run inside that window and there is no hush for an attacker to lift. The finding is that the safety of this depends entirely on that timing, and the timing is not what the code says it is relying on.

`onError` also cleared `sInProgress` before calling `radioResume`, which threw away the one piece of state that says whether the transfer ever started.

Fixed. The callback reads `sInProgress` first and resumes only when a transfer had really begun, so an invitation with the wrong password now reaches nothing. Retested on the radio afterwards: a wrong password is still refused, a killed transfer still brings the audio back.

CWE-691, control flow management. Availability only: there was no path here to reading or changing anything.

### Medium: the hush only covered one of the four ways the task reaches the tuner

Found by the code review after the first pass of this audit had already called the area clear, which is worth recording on its own: the audit read `radioHush` and the guard beside `pushToTuner` and stopped there.

The radio task writes to the tuner in four places, not one. Besides the push there is the squelch shortcut that sends a mute the moment the squelch opens or shuts, the tone for a beep, and the adaptive bandwidth extension. Only the push checked `sHushed`.

A reboot hides this, because it holds the hush for two hundred milliseconds and then restarts. An update over the air does not: it hushes when the transfer starts and holds it for the whole transfer, tens of seconds, while the hundred millisecond poll keeps running underneath. A squelch going from shut to open in that window sent `tef668xSetMute(false)` straight to the chip. That unmutes the radio in the middle of an update and puts a second task on the I2C bus while the flash is being written, which is the exact thing the flag exists to prevent and the thing check 282b says cannot happen.

Fixed. All four now check the flag, and the comment on `sHushed` says that every write has to, rather than leaving the next person to notice.

Availability and integrity: the bus contention is during a flash write. No path to reading anything.

### Decision: the hush flag is shared between tasks without a lock

CLAUDE.md says nothing mutable is shared without a lock. `sHushed` is written by whichever task is shutting the radio down and read by the radio task every round, and now has a second writer in `radioResume`. It is `volatile` rather than locked.

Taken deliberately. The radio task must be able to see the flag at a point where it cannot wait for a mutex, which is the whole reason the flag exists: `radioHush` reaches past the task to the tuner precisely because the caller is about to restart and cannot wait for the queue. A single byte store is atomic on this core, so there is no torn read.

Residual risk, written down rather than waved away: `volatile` gives visibility of that one byte and no ordering. `radioHush` sets `sHushed` first and writes `sLastPushedVolume` and `sLastPushedMute` afterwards, and `radioResume` relies on the radio task seeing those two. The two cores share internal SRAM coherently, so this holds on this hardware, but it holds because of the hardware and not because the code asked for it. If either variable moves to a place without that guarantee, this breaks quietly and the symptom is the audio coming back at the wrong volume.

### Decision: an authenticated caller can wear the flash with abandoned updates

Starting an update and abandoning it repeatedly erases the inactive application partition each time. It needs the OTA password, which is the access PIN, and anyone holding the PIN can already write whatever firmware they like. So this is not an escalation and no limit is being added.

### Checked and clear

- **The five corrected refusal messages disclose nothing.** All five sit after `requireAuth(false)`. Confirmed on the radio: a signed out caller posting rubbish to `/api/band`, `/api/mode`, `/api/pot`, `/api/squelch` and `/api/fm` gets "Enter the access PIN first." and never reaches the message. They name argument names only, and those are in README.md already.
- **The bandwidth ramp cannot wedge the radio silent.** `filterMoving` is false whenever the band or the frequency is also moving, so a retune and a filter change arriving together go out on the retune path, which mutes and unmutes around itself. It is false when the ramp is switched off mid ramp, and the filter then goes through `pushToTuner` with the chip already muted. The held back filter is released on the round `heard.muted` becomes true, which is bounded by the ramp length, and the loop wakes every twenty milliseconds while ducking, so it cannot spin. A bandwidth the state machine refuses never reaches `wanted`, so it cannot start a ramp that has nothing to finish.
- **`radioResume` is not reachable from the HTTP surface.** No endpoint calls it. The OTA error callback is the only caller.

## Phase 4 addendum: the panel light and the smoothed meter

Audited on 13 September 2026, against `ede6b5c` plus the working tree. Threat model is an attacker on the same LAN or in Wi-Fi range, not the internet. Scope: `core/backlight.c` and its use in `screen_task.cpp`, the backlight no longer being switched on inside `displayBegin`, the four version 7 settings fields and their migration from a version 6 blob, the four new `/api/settings` keys `blt`, `bdm`, `bds` and `blf`, the new `pnl` block and `sav` field in the state document, and `inputActivity` in `input_task.cpp`.

Result: **GREEN.** No critical and no high findings. Two medium, eight low, and two recorded decisions. All ten findings are fixed. Three were found on the radio rather than in a test or a review, which is the argument for the manual checklist existing at all, and one was found only because the review was run a second time after the change had moved.

### Low: a dim delay shorter than the boot would dim the panel as the radio came up

`backlightInit` runs inside `screenTaskBegin`, which is the third thing `setup()` does. Everything after it, the tuner patch, the radio task, the input layer and the Wi-Fi join, runs with nothing moving the backlight along, and the Wi-Fi join alone takes several seconds.

So the idle clock started when the panel was lit rather than when the radio was usable. On a radio set to dim after ten seconds and taking twelve to come up, the first `screenTaskPoll` found the delay already past and dimmed the panel in the same instant the radio finished booting, in front of the person who had just switched it on.

Availability of the display only, and self correcting: any input brings it back. It is a finding rather than a quirk because a panel that goes dark exactly as the radio comes up is indistinguishable from a radio that has failed to start, which is the failure shape this project keeps finding.

Fixed. `screenTaskPoll` treats its first call as an input, so the clock starts when the radio is ready. Checklist row 302 covers the dim itself; this one shows as a radio that does not dim during boot.

CWE-1188, insecure default initialisation of a resource. Nothing is readable or changeable through it.

### Medium: switching the dim on dropped the panel at once

Found by the code review after this audit had already read `backlightSetConfig` and called it clear, which is worth recording for the same reason the phase 3 one was: the audit read the branch that was there and did not ask what the branch left out.

`backlightSetConfig` restarted the idle clock only when the new delay was 0. Changing it to any other value left `lastInputMs` where it was, so the new delay was measured against a radio that had already been idle, and the next `backlightUpdate` found it past.

The concrete case is the ordinary one. Somebody spends a minute on the settings page, sets Dim after to ten seconds, and presses Apply. The panel starts fading down within milliseconds instead of after ten seconds, and it does it while they are looking at the control that caused it.

Availability of the display only, and an input lifts it. It is recorded at medium rather than low because the symptom is a panel going dark immediately after a setting was applied, which reads as the setting having broken the radio.

Fixed. Any change to the delay clears the dimmed flag and restarts the clock, in both directions. Changing only the levels still leaves the clock alone, because seeing a dim level while it applies is what makes it choosable. Checklist rows 310a and 310b cover it, and two tests do.

CWE-665, improper initialisation.

### Low: the fade at boot was invisible, so the feature did nothing a person could see

Found on the radio, not in a test, and not by looking at the code, which was correct throughout.

The fade was built at four tenths of a second to match the start up chime. On the radio it could not be told from the light switching on. Checked blind rather than by impression: the fade was switched on for one boot and off for another, in an order picked at random and not looked at until afterwards, and the two were indistinguishable. Reshaping the ramp to be even in perceived brightness rather than in duty did not change that either.

Not a security finding by itself. It is in this file because it is the shape this document keeps recording, arriving from the other direction: not a component reporting something untrue, but a feature reporting nothing at all, where doing nothing and working correctly look identical. Every gate was green, the code was right, and the only thing that separated "the fade works and is subtle" from "the fade never runs" was a deliberate test.

That test was worth building. A diagnostic firmware with the fade at two and a half seconds made it obviously visible, which settled that the mechanism ran and the duration was the only problem. Without it the honest outcome would have been to record the feature as unproven.

Fixed by measurement rather than by taste. 400 ms cannot be told from a snap, 1000 ms reads as a fade, 2500 ms is obviously slow, so both fades are a second. Written down in the backlight section of HARDWARE.md, and checklist row 295a says to do the comparison blind when in doubt.

### Low: the smoothed meter was smoothed and still unreadable

Found on the radio by the person looking at it, after every gate was green and the API said the smoothing was working.

`sav` does what it claims: on a steady FM station it takes the swing from about 3.2 dB to 1.6. The panel was still flickering, because it printed one decimal place and the smoothed value moves a tenth or two between readings. The last digit changed on forty of fifty nine consecutive samples. So the feature was correct, measurable, and useless for the thing it was asked to do.

The same shape as the row above it and worth keeping separate from it: not a component lying, but a measurement that answered a question next to the one being asked. "Is the value smoothed" was true. "Does the screen sit still" was false, and only the second one was in the ticket.

Fixed by measurement rather than taste, and the user's own suggestion was tested against it rather than taken. A longer display average was proposed; replaying the captured readings showed it barely moves the spread, because what is left is the signal really moving, and it costs up to three seconds of lag. Whole dB held until the level moves a whole dB away does better with no lag, one change in twenty four seconds against twelve. The one second average is left exactly as it was, which matters because the squelch, the seek and the bandwidth extension have thresholds measured against it.

`SignalDisplay` in `core/signal.h`, seven tests, and the working is in the backlight and signal sections of HARDWARE.md.

### Low: a checklist row asked for a needle this radio does not have

Row 317, written in this change, asked the reader to watch the analogue S-meter and see the needle sit still. No meter is fitted on this unit. That was already recorded in HARDWARE.md on 12 September 2026 and stated in the checklist at line 273, and the row was written anyway.

Nothing in the firmware is wrong: pin 27 is driven with the smoothed level, and the pin map comes from a firmware that runs on boards in this family that do have a meter. The defect is in the document, and it is the one this project has hit twice before, a check describing behaviour that never existed. A checklist that asks for something impossible teaches the reader to skip rows.

Row 317 now says there is nothing to do on this unit and that the needle half of the change is written but unproven until a board with a meter is in hand. Row 322 was rewritten in the same pass: it asked the reader to pull the aerial down until readings start failing, which does not make an I2C read fail, it only makes the level low.

### Medium: the held signal number latched the station that had just been left

Found by the second code review. The first had already read this area and passed it, correctly, because the code with the defect in it was written afterwards. That is the finding behind the finding, and it is now written into the build-ticket skill: a review of the state before the last two fixes is not a review of what ships.

The dial and the reading do not move together. The frequency changes as soon as the command is worked through; the reading keeps its own hundred millisecond cadence. So a snapshot exists carrying the new frequency and the previous station's level, which `radio_task.h` already said in as many words.

The screen started its held number again when it saw the frequency change, and was then handed that stale level and latched it, with a full dB of hysteresis around it. Tuning from a station reading 24.4 dBuV to one reading 24.9 left the panel showing 24 for as long as you stayed there. The reset existed for exactly this case and was defeated by it.

It passed every check because checklist row 319 had been rewritten, for an unrelated reason, to use an empty channel. A 34 dB jump clears a one dB band whatever the reset does.

Fixed in two parts. The snapshot now carries `levelSmoothedValid`, which says whether the level was read where the dial now is. And the waiting is in `core/signal.c` rather than in `screen_task.cpp`, because it is a decision with timing in it and the version in the task file could not be tested on a PC. Four tests cover it, including the 24.4 to 24.9 case that cannot be arranged on air.

CWE-672, operation on a resource after it is no longer valid.

### Low: the coverage gate could not show a new file

Not in the firmware, but in the gate that is supposed to prove the firmware is tested. `gate_coverage` piped `gcovr` through `tail -10`, and the table had grown past ten lines. `src/core/access_pin.c` and the new `src/core/backlight.c` were both cut off the top of what was printed.

The percentage and the floor were still correct, so nothing was ever passed that should have failed. The problem is what a person reads: a file with no coverage at all would not appear in the output, and its absence looks exactly like it not existing. That is the same failure shape as the rest of this file, applied to the tooling.

Fixed, `tail -30`. Confirmed by rerunning the gate and seeing all nine files listed.

### Decision: `pnl.dim` tells an unauthenticated caller whether anybody is using the radio

`GET /api/state` needs no PIN, by design, and now carries `pnl.dim`, which is true once the radio has been left alone for the configured delay. Anyone who can reach the radio can poll it and learn roughly when somebody last touched it.

Accepted, because it is not new information. The same document already carries `inp.lms`, the millisecond timestamp of the last input event, and `inp.clk` and `inp.prs`, the counts of knob clicks and presses since boot. Those answer the same question more precisely than a single boolean does. Making `pnl` need the PIN while `inp` does not would be a fence with nothing behind it.

Residual risk, written down rather than waved away: the whole open half of the state document is a presence signal for the room the radio is in. If the reads are ever put behind the PIN, `inp` and `pnl` go together.

### Decision: an authenticated caller can make the panel unreadable

With the PIN, `bdm=0` and `bds=1` make the panel go completely dark one second after the last input. The radio keeps working, keeps serving and keeps reporting, and any input brings the light straight back.

Accepted and deliberate. Anyone holding the PIN can already replace the firmware, so this is not an escalation. The one thing that is guarded is the setting that cannot be undone from the radio: `blt`, the brightness while the radio is in use, has a floor of 5 per cent, because a panel driven to nothing while somebody is using it looks broken and the only control for it is the web page that has just gone dark. The dim level has no floor for the opposite reason: it is left on purpose and an input always lifts it. Decision 28, and checklist rows 299, 300 and 310.

### Checked and clear

- **The version 6 to version 7 migration cannot read a new field out of old padding.** `backlightPercent` lands at offset 143, inside the single byte version 6 wrote as padding after `beepStart`. `settingsFieldEndOfVersion(6)` returns `offsetof(Settings, backlightPercent)` rather than the written length, so the copy stops at 143 and the four new fields keep the defaults `settingsDefaults` put there. Covered by `a_version_6_blob_gets_the_defaults_for_what_it_never_had`, which deliberately fills that byte with `0xEE` first. The length checks in `settingsFromBlob` are unchanged: a blob must be exactly the size its version wrote, so a short or long one is refused rather than read as far as it goes.
- **The four new settings are range checked twice.** Once by `apiNumber` against the bounds in the `stored[]` table, and again by `settingsValid` over the whole struct before anything is written. The `fields[]` table gained its four entries and the `static_assert` that the two tables are the same length still holds, which is what stops a value landing in the wrong field.
- **`sav` and `pnl` cannot overflow the buffers they are built in.** `sav` goes into the same `char sig[200]` as the rest of the tuner block. The worst case for that format is about 115 bytes with every value at its widest, and `snprintf` is bounded in any case. `pnl` is appended to an Arduino `String`, which grows.
- **Nothing crosses a task boundary without a lock.** `sBacklight`, `sLastWritten` and `sFirstPoll` are written by `screenTaskPoll` and read by `screenTaskBacklightState`, and `screenTaskSetBacklight` writes them too. All three run on the loop task: `inputPoll`, `screenTaskPoll` and `webLoop` are called one after another from `loop()`, and the settings handler runs inside `webLoop`. `sActivity` is the same, written by `inputPoll` and read by `screenTaskPoll`. `sLevelSmoothed` is written by the radio task and read in `publish`, which the radio task calls, under the lock it already takes.
- **The boot fade cannot hang start up.** The loop in `screenTaskBegin` runs while `backlightFading` is true, and that is cleared by `backlightUpdate` once the elapsed time reaches `fadeMs`, which is at most `BACKLIGHT_FADE_UP_MS`, one second. The boot watchdog allows 45 seconds. Every comparison is on a difference, so a `millis()` wrap during the fade cannot extend it, and `the_millisecond_counter_may_wrap` covers that.
- **A panel that did not come up cannot leave a caller reading rubbish.** `screenTaskBegin` returns before `backlightInit` when `screenBegin` fails, and `sBacklight` is a static, so it is zeroed. `screenTaskBacklightState` then reports 0 and false, `screenTaskPoll` returns at once, and `screenTaskSetBacklight` guards its write with `sReady`.
- **`sav` is never staler than `sig`.** The code review asked whether the snapshot should be zeroed when the average is started again, since `publish` copies `sLevelSmoothed` on every round and the average reset does not clear it. It should not, and the finding is recorded as a decision rather than taken. `sLevelSmoothed` is only written when a reading arrived, and `sSnapshot.quality` is only copied when a reading arrived, so the two always describe the same read. For the one poll interval after a retune both still describe where the dial was, which is what the raw reading already did before any of this. Zeroing it would put 0.0 dBuV on the panel instead, and a level of zero is a real reading a dead band produces, so that would be the worse lie. The comment on the field now says exactly what the reset does and does not do.
- **The new arithmetic cannot overflow or leave its range.** Checked by brute force rather than by reading: `isqrt32` agrees with a real square root for every percentage 0 to 100, its largest result is 1000 and the largest square 1,000,000, well inside a signed 32 bit int. The fade level was evaluated for every pair of endpoints at every point along the ramp and never leaves 0 to 100. `signalDisplayLevel` was walked over every starting point and every reading from -200 to 1200 tenths and the held number is never more than 0.9 dB from the reading it stands for.
- **The held signal number cannot be stuck by a stale reading.** The dial and the reading do not move together, so a snapshot exists carrying the new frequency and the previous station's level. `levelSmoothedValid` says which, and the screen waits for a reading taken where the dial now is before starting its held number again. Found by the second code review, after the first had passed the same area, because the code it applies to was written afterwards.
- **`screenTaskSignalShown` is read on the task that writes it.** It is called from `buildState`, which runs inside `webLoop`, and written by `screenTaskPoll`. Both are called from `loop()`, one after the other, the same as the backlight state beside it.
- **`displayBegin` leaving the backlight off cannot strand a lit panel dark.** `screenBegin` is the only caller, and `screenTaskBegin` is the only caller of that. There is no path that starts the panel without bringing the light up afterwards.


## Phase 3 addendum: what belongs to a band, and the radio saving itself

Audited on 13 September 2026, against `e641bb6` plus the working tree. Threat model is an attacker on the same LAN or in Wi-Fi range, not the internet. Scope: the per band arrays in `RadioSettings` and `Settings`, settings version 8 and its migration from version 7, `core/autosave.c`, `src/settings_task.cpp` and the automatic write to NVS, the shared `settingsBuildCandidate`, and the new `asv` block in the state document.

Result: **GREEN.** No critical findings. Two high, three medium, four low, and one recorded decision. All nine findings are fixed.

The review was run twice, because the change moved after the first run. The second run found five more, one of them the worst of the lot for what this feature is meant to protect. That is now the rule in the build-ticket skill: a review of the state before the last fixes is not a review of what ships.

### High: tuning out of a band by frequency lost everything but the dial

`RADIO_TUNE` across a band edge wrote `bandFreqKHz` by hand rather than putting the whole band away, so the width, the step and the mode of the band being left were dropped. Its own comment claimed it behaved exactly as the BAND button does, and that had stopped being true the moment the other three were added.

Typing a frequency on the keypad is the usual way to leave a band, so this undid most of the ticket on the most common route out. Set medium wave to 6 kHz and 1 kHz steps, type 98.3, press BAND back to medium wave, and it was 4 kHz and 9 kHz again.

Not a security finding in itself. It is here because it is the shape this file keeps recording: one path kept a promise and another did not, and both looked identical from outside. A duplicated three lines is how the two came apart, and the fix is that there is now one `rememberBand` and both paths call it.

CWE-691, control flow management. Availability of stored state only.

### High: the band the radio came up on never got its own settings back

`radioDefaults` leaves the radio on FM. `radioFromSettings` then asked for the stored band through a `RADIO_SET_BAND` command, and that command returns early when the radio is already on the band being asked for. So a radio whose stored band was FM took the early return, `settleAfterBandChange` never ran, and the stored FM step, width and mode were silently ignored. Stored 50 kHz, got 100.

The early return is right in use and wrong here, which is why the fix is to settle the band directly rather than through the command.

It had a second effect worth recording on its own: what came out of the settings did not go back in unchanged, so the new automatic save found a difference on every boot and wrote to NVS once per power cycle for nothing. Flash wear is the whole risk this feature was designed around, and it was writing on every start before anybody used the radio. Confirmed on the radio both ways: before the fix `asv.dif` was true at boot and `n` reached 1 within ten seconds; after it, `dif` is false from the first sample and `n` stays 0 across a reboot.

CWE-1188, insecure default initialisation. The wear is the part that matters.

### Medium: two owners of the AM width

The single `amBandwidthKHz` from before the per band arrays was applied at the end of `radioFromSettings`, over the top of the per band value, without updating the array to match. Two sources of truth for one value, with the older one silently winning.

Fixed by giving the array sole ownership. The old field now only fills a band that has none of its own, which is what a blob written before the array existed carries, and it is written into the array at the same time so nothing reads it twice.

### Medium: a test that passed without running the code it was testing

`a_width_from_the_wrong_side_is_never_restored` planted an illegal FM width while the radio was still on FM. Leaving the band put the live width away over the top of it, so the value under test was gone before the test reached it and the assertion passed on a path that had nothing to do with the rejection.

Recorded rather than quietly fixed because a green test that proves nothing is worse than a missing one: it is counted as coverage and it is believed.

### Low: the manual save took two snapshots of the radio

`handleApiSave` read the radio once for its reply and `settingsBuildCandidate` read it again for the blob. The dial can move between the two, and the message then names a station that was not the one written. Fixed by building the message from what was actually stored.

### Decision: an authenticated caller can still make the radio write to flash

`POST /api/save` writes NVS on demand and is behind the PIN. SEC-05 already recorded that nothing rate limits it, accepted because a write needed somebody to ask.

The automatic save does not change that reasoning, and it deliberately does not add a rate limit of its own beyond the ten second wait. What it does change is that writes now happen without anybody asking, so the protections are worth stating: it writes only when what the radio is set to actually differs from what is stored, never while a seek is walking the band, and any write from any path starts the wait again. Measured on the radio: twenty retunes in ten seconds cost one write, and a radio nobody is touching writes nothing at all.

Residual risk, written down rather than waved away: somebody with the PIN can still drive writes as fast as the debounce allows by changing a setting every ten seconds, which is six an hour. That is far below anything that wears a sector, and it needs the PIN, and anybody holding the PIN can already replace the firmware.

### Medium: the automatic save chased the volume knob

Found by the second review, and it undercut the whole reason the feature was built carefully.

`radioToSettings` always writes the live volume into `startVolumeDb`, and the comparison that decides whether to save is over the whole struct. So every turn of the volume control made the settings differ and earned a write to flash ten seconds later, for a value decision 26 says is read back in one mode only: in manual squelch, where the knob is the squelch and nothing else says how loud to be.

The second half is worse and is the reason this is recorded rather than tidied away. The volume the radio starts at is mapped from a single pot reading through `potVolumeDb` with no hysteresis. A knob sitting near the boundary between two dB maps to a different value than the one stored, so the settings differ from the first poll and the radio writes flash ten seconds after a power cycle in which nobody touched anything.

That failure is intermittent, depends on where the knob happens to be sitting, and is invisible: `asv` would have shown one save and everything else would look normal. The hardware check run before the review passed only because the knob happened to land on the same value. It is the shape this file keeps recording, arriving through flash wear instead of through audio.

Fixed by putting the stored volume back unless the squelch is manual. Confirmed on the radio afterwards: twelve volume changes cost zero writes, and tuning still saves normally.

CWE-1050, excessive platform resource consumption within a loop.

### Low: the band the radio came up on could lose its remembered dial position

Introduced by the fix for the second high finding above, and caught in the same pass. `radioFromSettings` settled the start band and then set the frequency to the bottom of it before applying the stored one. Normally harmless, because the stored frequency lands in the same band. But that path exists for the case where the region or the medium wave spacing has moved under the stored frequency, and then it resolves to a different band, which is a band change, which puts the current band away: the bottom of the band gets written over the station it was left on, and the automatic save writes that ten seconds later.

Fixed by starting from the band's own remembered frequency, clamped, the way `RADIO_SET_BAND` already does.

### Low: three endpoints wrote NVS without restarting the wait

The Wi-Fi, PIN and pot calibration handlers all write NVS and none of them told the automatic save. A tuning change nine seconds into its wait, followed by a PIN change, wrote NVS twice inside a second. Decision 29 claims the two paths cannot take turns writing, and for those three it was not true. All five writing endpoints now call `settingsTaskSaved`.

### Low: the countdown was read one step early

`asv.due` was computed before the call that restarts the clock, so while a hand was on the knob it reported the wait left from the previous look rather than the full length. The field exists so the checklist can watch the countdown, so a countdown that never shows its real value defeats it.

### Checked and clear

- **The version 7 to version 8 migration takes all of version 7 and none of version 8.** `offsetof(Settings, bandFreqKHz)` is 148 and version 7's own size is 148, so version 7's fields ran to the end of its struct with no trailing padding for a new field to land in. Both numbers are pinned by `a_version_7_blob_gets_the_defaults_for_what_it_never_had`, which also checks every band comes back unset.
- **A stored value is never trusted against the band it is restored to.** The step is checked with `bandStepAllowed`, the width with `bandBandwidthAllowed` and the mode with `radioTuneModeAllowed`, each falling back to that band's own default. That matters because the band plan moves under stored values: a step legal at 9 kHz medium wave spacing need not be legal at 10. An AM width restored onto FM would pin the filter a tenth of what a station needs and read exactly like a radio with no aerial, which is why that one is checked rather than assumed.
- **The stored tuning mode cannot index outside its enum.** `settingsValid` refuses any entry at or past `TUNE_MODE_COUNT`, and `radioFromSettings` clamps again on the way in.
- **The automatic save cannot write a blob the next start would refuse.** `settingsValid` runs on the candidate before `settingsNvsSave`, and a refusal restarts the wait rather than retrying every quarter second for as long as the radio stays in that state.
- **Nothing crosses a task boundary without a lock.** `settingsTaskPoll` runs on the loop task alongside `inputPoll`, `screenTaskPoll` and `webLoop`, and it reaches the radio only through `radioGetSnapshot`, which takes the lock. `settingsTaskStatus` is read from `buildState` inside `webLoop`, the same task that writes it.
- **The wait survives the millisecond wrap.** Every comparison in `core/autosave.c` is on a difference, and `the_millisecond_counter_may_wrap` walks it across the boundary.


## Correction: the FM de-emphasis was working all along

Written on 13 September 2026. This corrects the finding earlier in this file which concluded that the de-emphasis command was probably not reaching the chip or not being acted on. That conclusion was wrong, and it is corrected here rather than edited out, because this file is appended to and because how it went wrong is the useful part.

**What the earlier test said.** Two blind A/B tests on FM 106.4 MHz, 75 us against 50 us and then off against 50 us, both heard as no difference. The reasoning was sound as far as it went: switching de-emphasis off removes the treble correction altogether, so a null result there points at the command not landing.

**What was actually true.** Four blind A/B pairs, off against 50 us, all four called correctly. One pair had the order reversed on purpose and the answer moved with it, so an order effect does not explain it. One in sixteen by chance. The de-emphasis works, the command lands, and no code needed changing.

Two things were wrong with the first test, and neither was in the firmware.

**The test signal was wrong.** It used music on a station. De-emphasis is a treble shelf, and the loudest treble a radio produces is hiss, not music. On an empty channel the difference is obvious even on the internal speaker, which rolls off the top of a song enough to hide it. Changing the test signal was what turned four null results into four correct calls.

**There was an unaccounted confound.** The stored weak signal high cut start was 35 dBuV, and the test station was reading 33 to 37, so the chip's own treble roll off was switching itself on and off during a test about treble. Confirmed while investigating: with the start at 35 the reported `cut` flickered between 0 and 6 as the signal crossed the threshold, and with it off `cut` held steady at 0. That value was visible in `/api/state` the whole time and nobody looked at it.

**What this says about the method.** Everything measurable had already been checked and all of it was right: the command encoding is byte for byte what the reference firmware sends, `deemphasisUs` is in the list that triggers a feature push so a change lands without needing a retune, and the driver returns OK. The investigation then reached for the conclusion that the chip was lying, because that is the failure this project keeps finding, and it is the one this file is mostly about.

It is worth writing down that the habit cut the wrong way here. A radio that reports a setting it is not applying and a test that cannot detect a setting being applied look identical from the outside. The first was assumed because it is the familiar one. The check that separates them is to ask what the test could detect before concluding anything from what it did not, and the standing instruction for that is now checklist rows 191a and 191b.

No finding, no fix, and nothing to record as a residual risk. The control stays.

## Phase 3 addendum: the auto squelch on the shoulder of a strong station

Audited on 13 September 2026, against `64ab854` plus the working tree. Threat model is an attacker on the same LAN or in Wi-Fi range, not the internet. Scope: the FM level floor and the opening window in `core/squelch.c`, the level average the squelch now keeps, `squelchRetuned` and its call from the radio task, settings version 9 and the new `sqf` key, and the new capture and generator under `test/fixtures/squelch/`.

Result: **GREEN.** No critical and no high findings. Four medium, four low, and one recorded decision. All eight findings are fixed.

The review was run twice. The second run found four more, two of them regressions introduced by the first round of fixes, which is now the third ticket in a row where rerunning after the change moved was what caught the real defect.

### Medium: the fix would have muted a station sitting on the limit, twice over

Not a security finding. It is here because it is the failure this file exists to record, and because it was introduced, caught, half fixed, and only then fixed properly.

Opening was changed to need more than one good reading, so that the isolated readings the channel beside a strong station produces could not unmute the radio for a full second each. Written as two readings in a row, that is worse than the fault it fixes. A signal sitting exactly on a limit alternates good and bad from one reading to the next, so it never produces two together.

The first version of it also stopped a single good reading cancelling a shut that was already being held, which would have muted a station already playing. An existing test caught that one. The second version fixed the already-open case and left the shut case broken, so a station on the limit that started muted would have stayed muted for ever, and in manual mode, where the raw level is judged against the person's own threshold and jumps several dB between readings, a threshold set near the signal would have silenced the radio permanently.

Fixed by counting two of the last three readings rather than two in a row. Alternating readings reach that on the second good one; the shoulder readings, which were three apart, never do. Staying open still takes one reading. Four tests cover it, including the two shapes that were got wrong.

CWE-670, always incorrect control flow implementation. Availability of the audio.

### Medium: the capture the threshold was fitted to was not measuring what it claimed

`signalAverage` forgets per reading, not per millisecond. The capture was taken over HTTP at about three readings a second and the radio judges the squelch at ten, so replaying the captured column through the average applies a smoothing three times heavier than the radio does. The shoulder figure of 18.2 dBuV that the floor was first fitted against is a number this radio never produces.

The same capture also recorded about 40 per cent of its lines twice, because the sampler did not check the snapshot sequence number, and duplicated samples make a signal look steadier than it is. Both errors flatter the result in the same direction.

Retaken with every line a distinct snapshot, and the radio's own smoothed level captured alongside the raw one so the floor is judged against the number the radio actually had rather than a replay at the wrong rate. On the clean capture one shoulder smooths to 16.2 dBuV, above the floor, where the discarded one said 18.2 and an earlier afternoon reading said 13.3.

Recorded at medium because a threshold fitted to a mismeasurement is exactly what CLAUDE.md bans, and every gate was green while it was wrong.

### Medium: the level floor could be switched off by a value somebody might want

`fmLevelFloorTenths` used 0 to mean no floor. A dead channel on this radio reads a little below zero, so 0.0 dBuV is a floor somebody could reasonably ask for, and it collided with off. Fixed with a sentinel, so 0.0 is a usable value. The setting exposed to a person keeps 0 meaning off, which is the idiom every other setting here uses, and that is stated rather than left to be discovered.

### Medium: a test passed without running the code it was named after

`the_weakest_station_on_air_is_never_muted` replayed a station reading 31 to 34 dBuV against a floor of 15, which is 16 dB of margin, so it could not have failed whatever the floor did. The station the threshold actually turns on is the 19.6 dBuV one, which is not in the capture at all.

Renamed to say what it does, and a separate test added for a station just above the floor with the spread a real signal has rather than a flat line.

### Low: the lock protected nothing

`radioSetSquelchFloor` took the lock to write the config and the radio task read it without taking the lock, so the lock gave no protection and the comment saying it did was wrong. Today only one aligned field ever changes, so nothing tears, but a second settable field would have made it a real race with nothing to warn anybody. The task now copies the config out under the lock, the same way it already copies the mode and the threshold.

### Low: state that belonged to one rule was carried into another

A mode or band change starts the hold again, on the stated reasoning that a decision begun under one rule must not count towards a decision made under another. The new run of good readings was not being cleared with it, so a reading judged good under the FM rule could count towards opening under the AM rule or under a person's own manual threshold.

### Low: the floor is off for a moment after every retune

The level average is started again on each retune, and the floor waits for a few readings before it is applied, so there is about three tenths of a second after each step of the dial where the floor does nothing.

Left as it is and written down rather than fixed. It is the right way round: the floor exists for a radio left sitting on the channel beside a strong station, and a dial being turned is not sitting anywhere. Applying the floor to the first reading instead would risk muting a station whose reading arrived before the tuner had settled, and muting a station is the fault this squelch is least allowed to have. The settle was shortened from five readings to three to narrow the window.

### Low: the generated header and the generator

The capture generator read field values with a pattern that stops at a dot, so a capture written with a decimal point would have been read as the part before it, out by a factor of ten and silent about it. It now refuses anything that is not a whole number and says which line. The generated header also has to be run through clang-format, which the format gate covers like any other file, and the generator now says so.

### Decision: seek can stop on something the auto squelch then mutes

Seek has its own level floor, judged on the raw reading, running from 19.0 dBuV at sensitivity 1 down to 4.0 at sensitivity 6. At the default of 4 that is 10.0 dBuV, which is below the squelch floor of 15.0. A reading in the capture would do it: raw 20.5 passes seek's test while the smoothed level fails the squelch's. The radio would stop on a frequency, play for a second, and go quiet.

Tested rather than assumed. Three seeks from below each of the two shoulders stepped past them and stopped on real stations with the audio open, because seek's noise and multipath tests reject the shoulders even though its level test alone would not.

Accepted rather than fixed, because the two numbers answer different questions. The seek sensitivity is a choice about how hard to hunt and a person is expected to move it. The squelch floor is a claim about what a station looks like on this radio. Coupling them would mean turning up the seek sensitivity quietly changed when the radio goes silent, which is worse than the case being documented.

Residual risk, written down rather than waved away: at high seek sensitivity on a band with strong stations, a seek can stop somewhere the audio will not open. Checklist row 152g is the check and it says to report it rather than nudge either number.

### Checked and clear

- **The version 8 to version 9 migration takes all of version 8 and none of version 9.** `fmSquelchFloor` sits at offset 193, inside the three bytes version 8 wrote as padding, so version 9 is the same length as version 8 and only the version field separates them. Both the hand written size and the field end are pinned by a test that fills that padding with a pattern first.
- **The new setting cannot ask for something that mutes the radio.** `sqf` is range checked by `apiNumber` against 0 to 40 and again by `settingsValid` over the whole struct before anything is written. Every station measured here reads above 19.6 dBuV, so the ceiling is well below anything that would silence the band.
- **The setting reaches the squelch rather than only being stored.** Confirmed on the radio, which matters because the first attempt to check it proved nothing: with the floor off the shoulder stayed shut anyway, because the noise and multipath tests were already rejecting it, so both settings gave the same answer. Rechecked on a station at 25.1 dBuV, where a floor of 15 gave 15 of 15 readings open and a floor of 40 gave 0 of 15.
- **A failed reading never enters the level average.** A failed read leaves the previous values in the struct, so feeding it again would count the same sample twice, which is the error the capture itself made and which is now tested for in the code.
- **Nothing new crosses a task boundary unprotected.** The squelch state is touched only by the radio task. The config is written from the web task and copied out by the radio task under the lock that already guards the mode and the threshold.
